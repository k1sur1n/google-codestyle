# MLOps: профиль Google

> Данные актуальны на 2026-10-09.

Единого «стандарта MLOps» у Google нет, но есть устойчивый набор письменных принципов: гайд Rules of Machine Learning (43 правила, обновлён 2025-08-25), статьи «Hidden Technical Debt in Machine Learning Systems» (2015) и «The ML Test Score» (2017), документ Google Cloud об уровнях зрелости MLOps 0/1/2 (ревизия 2024-08-28) и документация TFX. Профиль превращает их в проверяемые правила: артефакты версионируются и лежат вне git, обучение оформлено пайплайном с проверкой данных, модель перед выкладкой проходит две проверки (качество и совместимость с инфраструктурой), выкатывается постепенно и может быть откачена, а готовность к продакшену считается по рубрике ML Test Score. Письменных правил Google про Git LFS, DVC и про запрет коммитить данные и веса нет - публичных данных не найдено; эти места закрыты альтернативами с пометкой «не Google». Почти все правила имеют уровень SHOULD, потому что источники формулируют их как рекомендации.

Области идентификаторов: `G-MLOPS` (этот документ), `G-LIB` ([libraries.md](libraries.md)). Структура проекта и конфиги экспериментов - в [project-structure.md](project-structure.md), ноутбуки и очистка выводов - в [notebooks.md](notebooks.md), сиды, детерминизм, фиксация окружения и трекинг экспериментов - в [reproducibility.md](reproducibility.md). Шаблоны карточек: [MODEL_CARD.md](../../templates/ml/MODEL_CARD.md) и [DATA_CARD.md](../../templates/ml/DATA_CARD.md).

Как читать строку «Источник»: тип описывает сам источник, пометка «не Google» означает, что это не правило и не практика Google, пометка «реконструкция» - что правило сформулировано авторами профиля по нескольким источникам, а в источнике нормой не названо.

### 1.2. Чего нет

Публичных данных не найдено по следующим темам:

- правило Google «не коммитьте данные и веса моделей в git» - есть только рекомендации, где хранить каждый вид артефактов, и практика примеров;
- рекомендации Google по Git LFS и DVC для ML-репозиториев;
- отдельный документ Google о процедуре отката модели - откат упоминается в четырёх источниках одной-двумя фразами (см. раздел 7);
- публичный стайлгайд для C++-кода LiteRT (бывший TensorFlow Lite) и XLA;
- актуальный официальный Markdown-шаблон model card: Model Card Toolkit в архиве с 2024-09-27;
- официальное заявление о статусе TFX (активная разработка или режим поддержки). Вывод «жив, но развивается медленно» сделан по релизам.

Продуктовая документация Vertex AI (с апреля 2026 года продукт называется Gemini Enterprise Agent Platform, адреса страниц по-прежнему содержат `vertex-ai`) в этом профиле используется только на уровне определений: значения порогов по умолчанию и детали настройки мониторинга и выкладки не проверялись.

## 2. Уровни зрелости MLOps

Документ Google Cloud описывает три уровня автоматизации. Это шкала, а не чек-лист: документ не требует уровня 2 от всех, он нужен, когда пайплайнов много и они часто меняются.

| Уровень | Название в источнике | Что автоматизировано | Признаки | Что болит |
|---|---|---|---|---|
| 0 | MLOps level 0: Manual process | ничего | шаги ручные, на скриптах и ноутбуках; обученную модель передают инженерам как артефакт; релизы несколько раз в год; нет CI и CD; выкладывается только сервис предсказаний; предсказания не логируются и не мониторятся | модель не адаптируется к изменению данных; передача «исследователь → инженер» порождает training-serving skew |
| 1 | MLOps level 1: ML pipeline automation | обучение (continuous training) | шаги эксперимента оркестрованы; один и тот же пайплайн в разработке и в продакшене; компоненты модульные, в идеале в контейнерах; выкладывается весь обучающий пайплайн, а не только модель; добавлены валидация данных и модели, хранилище метаданных, триггеры | сами пайплайны тестируются и выкатываются вручную |
| 2 | MLOps level 2: CI/CD pipeline automation | сборка, тесты и выкладка пайплайнов | система контроля версий, сервисы тестов и сборки, сервис выкладки, реестр моделей, хранилище признаков, хранилище метаданных, оркестратор; шесть стадий от разработки до мониторинга | анализ данных и анализ модели остаются ручными |

Триггеры переобучения на уровне 1: по требованию, по расписанию, по появлению новых данных, при деградации качества, при значимом сдвиге распределений. Валидация данных там же различает два случая: расхождение схемы останавливает пайплайн до разбора, сдвиг значений запускает переобучение.

Три термина из документа, которыми пользуется профиль: CI в ML проверяет не только код, но и данные, схемы данных и модели; CD доставляет обучающий пайплайн, который сам разворачивает сервис предсказаний; CT (continuous training) - автоматическое переобучение и выкладка моделей, свойство только ML-систем.

Интерпретация: для репозитория без облака Google переносимы три вещи - перечень CI-тестов уровня 2 (G-MLOPS-014), проверки перед выкладкой (G-MLOPS-017, G-MLOPS-018) и принцип «один пайплайн в разработке и в продакшене» (G-MLOPS-008). Выбор оркестратора документ не предписывает.

## 3. Артефакты: что версионировать и что не коммитить

### 3.1. Сводка

| Что | Письменное правило Google | Что делает профиль |
|---|---|---|
| Данные | нет: публичных данных не найдено. Есть рекомендация хранить неструктурированные данные в объектном хранилище, структурированные - в хранилище данных | не коммитить; в git - код загрузки и указатель на версию (G-MLOPS-002) |
| Веса, чекпойнты, экспортированные модели | нет: публичных данных не найдено. Есть рекомендация держать модели в реестре | не коммитить; версия в реестре или объектном хранилище (G-MLOPS-002, G-MLOPS-007) |
| Секреты | общее правило Google Open Source: перед публикацией убрать конфиденциальную информацию; ML-специфики нет | не коммитить; сканер секретов в pre-commit и CI (G-MLOPS-004) |
| Выводы ноутбуков | правило проекта `tensorflow/docs`: CI отклоняет изменённые ноутбуки с выводами; во Flax и JAX выводы сохраняются | см. [notebooks.md](notebooks.md) |
| Изображения и другие сгенерированные бинарные файлы | правило TensorFlow docs style: изображения, как правило, не коммитятся | не коммитить (G-MLOPS-005) |
| Каталог запуска (логи, события TensorBoard, чекпойнты) | практика примеров Flax: каталог задаётся флагом `--workdir` и лежит вне репозитория | `.gitignore` для локальных каталогов запусков |

Известное расхождение: монорепозиторий `google-research` хранит датасеты прямо в git (они выпущены под CC BY 4.0) и из-за размера советует скачивать один подкаталог или делать `git clone --depth=1` ([README](https://github.com/google-research/google-research/blob/master/README.md)). Профиль этот вариант не берёт: он решает задачу публикации статей, а не командной разработки.

### 3.2. Правила

### G-MLOPS-001 · SHOULD · Код, данные и модели версионируются, и каждый вид артефактов хранится в своём хранилище: код и определения пайплайнов - в git, данные - в объектном хранилище или хранилище данных, модели - в реестре, образы контейнеров - в реестре артефактов
- Проверка: ручное ревью архитектуры; в README проекта перечислено, где лежит каждый вид артефактов.
- Источник: [AI and ML perspective: operational excellence](https://docs.cloud.google.com/architecture/framework/perspectives/ai-ml/operational-excellence) (2025-04-28) · официальный гайд · высокая; [Best practices for implementing ML on Google Cloud, раздел об организации артефактов](https://docs.cloud.google.com/architecture/ml-on-gcp-best-practices) (2024-09-09) · официальный гайд · высокая.

### G-MLOPS-002 · SHOULD · Данные, веса и чекпойнты не коммитятся в git; в репозитории лежат код загрузки, конфиги и указатель на версию артефакта
- Проверка: частично: хук `check-added-large-files` из `pre-commit/pre-commit-hooks` (порог по умолчанию 500 КБ, меняется `--maxkb`), шаблоны в `.gitignore`; остальное - ручное ревью.
- Источник: [Best practices for implementing ML on Google Cloud](https://docs.cloud.google.com/architecture/ml-on-gcp-best-practices) (2024-09-09) · официальный гайд · средняя · реконструкция; [пример Flax MNIST: датасет скачивается при запуске, рабочий каталог - вне репозитория](https://github.com/google/flax/blob/main/examples/mnist/README.md) (HEAD 2026-10-07) · практика, выведенная из репозиториев (один пример, доля не измерялась) · средняя. Прямого запрета у Google нет; он есть у Cookiecutter Data Science: [Opinions](https://cookiecutter-data-science.drivendata.org/opinions/) (v2.3.0, 2025-07-23) · сторонний источник · не Google.
- Пример:

```gitignore
# плохо: в .gitignore нет ничего про данные и модели, в истории лежит data/train.parquet

# хорошо: каталоги и форматы исключены, указатели остаются в git
/data/
/models/
/workdir/
*.ckpt
*.safetensors
*.keras
*.tflite
```

### G-MLOPS-003 · SHOULD · Если большой файл всё же должен жить рядом с кодом, он ведётся через DVC или Git LFS, а не обычным git
- Проверка: `git lfs ls-files` или наличие `.dvc`-файлов; `check-added-large-files` пропускает файлы, отслеживаемые Git LFS.
- Источник: [DVC: Get Started](https://doc.dvc.org/start) (версия на странице не указана, просмотрено 2026-10-09) · официальный гайд · высокая · не Google; [Git LFS](https://git-lfs.com/) (просмотрено 2026-10-09) · конфиг или инструмент · высокая · не Google. У Google публичных данных не найдено.
- Пример:

```bash
# DVC: в git попадают только data/train.parquet.dvc и .gitignore
dvc add data/train.parquet
git add data/train.parquet.dvc data/.gitignore
dvc push

# Git LFS: правило попадает в .gitattributes, файл - в LFS-хранилище
git lfs track "*.safetensors"
git add .gitattributes
```

Различие: DVC хранит в git маленький файл-указатель и умеет описывать пайплайн (`dvc.yaml`), а данные кладёт в настроенное удалённое хранилище (`dvc remote`); Git LFS прозрачен для обычных git-команд, а содержимое файлов хранит LFS-сервер, как правило у того же хостинга, что и репозиторий. Команда `git lfs track` не переносит в LFS файлы, которые уже есть в истории: для этого служит `git lfs migrate`.

### G-MLOPS-004 · MUST · Секреты (ключи, токены, пароли, файлы `.env`) не попадают в репозиторий; CI получает их из зашифрованных секретов платформы
- Проверка: хук `gitleaks` (`gitleaks/gitleaks`) и хук `detect-private-key` (`pre-commit/pre-commit-hooks`) в pre-commit и в CI; `.env` в `.gitignore`.
- Источник: [Google Open Source: Preparing for release](https://opensource.google/documentation/reference/releasing/preparing) (2025-06-10) · официальный гайд · высокая; [Keras governance: токены CI как encrypted secrets](https://github.com/keras-team/governance/blob/master/project_setup_best_practices.md) (2023-06-07, не обновляется) · производный гайд проекта · средняя. Уровень MUST: гайд Google Open Source требует убрать конфиденциальную информацию до публикации. Сканеры секретов и приём с `.env` - не Google: [Cookiecutter Data Science, Opinions](https://cookiecutter-data-science.drivendata.org/opinions/) · сторонний источник · не Google.

### G-MLOPS-005 · SHOULD · Изображения, графики и другие сгенерированные бинарные файлы не коммитятся вместе с документацией и ноутбуками
- Проверка: частично: `check-added-large-files`; остальное - ручное ревью.
- Источник: [TensorFlow documentation style guide](https://www.tensorflow.org/community/contribute/docs_style) (2021-2024) · производный гайд проекта · высокая. В TensorFlow изображения размещает команда документации, чтобы репозиторий не рос; в своём проекте их место - объектное хранилище или артефакты CI.

### G-MLOPS-006 · SHOULD · Входные данные читаются по версии или замороженному снимку, а не по указателю «последняя версия»
- Проверка: ручное ревью конфигов: в пути или идентификаторе датасета есть версия, дата снимка или хеш.
- Источник: [Hidden Technical Debt in ML Systems, §3 «Unstable data dependencies»](https://proceedings.neurips.cc/paper_files/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf) (NIPS 2015) · книга, статья или доклад · высокая. Фиксация версии датасета в TFDS описана в [reproducibility.md](reproducibility.md).
- Пример:

```python
# плохо: вчерашний и сегодняшний запуск читают разные данные
train_path = "gs://my-bucket/features/latest/"

# хорошо: снимок назван явно и записан в конфиг эксперимента
train_path = "gs://my-bucket/features/snapshot=2026-10-01/"
```

### G-MLOPS-007 · SHOULD · Каждая выкладываемая модель - неизменяемая нумерованная версия: в реестре моделей или в каталоге экспорта, последний компонент пути которого - номер версии
- Проверка: ручное ревью скрипта экспорта; в CD - проверка, что версия с таким номером ещё не существует.
- Источник: [Using the SavedModel format](https://www.tensorflow.org/guide/saved_model) (2024-03-23) · официальный гайд · высокая; [Introduction to Model Registry](https://docs.cloud.google.com/vertex-ai/docs/model-registry/introduction) (просмотрено 2026-10-09) · официальный гайд · средняя. Номер версии в пути - соглашение TensorFlow Serving.

## 4. Пайплайны обучения и инференса: принципы

Принципы ниже не зависят от платформы. Таблица показывает, как один и тот же принцип выглядит в TFX, в Kubeflow Pipelines (KFP; управляемые Pipelines в Vertex AI - KFP-совместимый бэкенд) и в репозитории без платформы.

| Принцип | TFX | KFP и управляемые Pipelines | Без платформы («не Google») |
|---|---|---|---|
| Шаг - отдельный компонент с объявленными входами и выходами | стандартные компоненты от ExampleGen до Pusher | компонент - одно исполнение контейнера; пайплайн пишется на Python SDK и компилируется в платформенно-нейтральный IR YAML | стадия в `dvc.yaml` с `deps`, `params`, `outs` |
| Данные проверяются до обучения | StatisticsGen → SchemaGen → ExampleValidator | компонент валидации перед обучением | тест схемы в начале пайплайна |
| Один код преобразований в обучении и инференсе | компонент Transform на TensorFlow Transform | общий модуль или образ | один модуль признаков, импортируемый обоими путями |
| Каждый запуск оставляет метаданные | ML Metadata: запуски компонентов, артефакты, конфигурация | метаданные платформы | трекер экспериментов, например MLflow |
| Модель выкладывается после двух проверок | Evaluator и InfraValidator выдают «blessing», Pusher выкладывает только при обоих | условие в графе пайплайна | два обязательных CD-джоба |
| Пакетный инференс - такой же компонент | BulkInferrer | компонент пайплайна | стадия пайплайна |

Статус инструментов. TFX не в архиве: в 2026 году вышли 1.17.3 и 1.21.0 (тег от 2026-06-17), но активность низкая, а файл [`ROADMAP.md`](https://github.com/tensorflow/tfx/blob/master/ROADMAP.md) не менялся с 2022-03-24 (последняя запись - Q2 2022; проверено по истории git 2026-10-16). Документ Google Cloud о лучших практиках среди рекомендаций по оркестрации называет управляемые Pipelines, Kubeflow Pipelines SDK, управляемый Airflow и Ray, а TFX там не упомянут. Kubeflow Pipelines - проект сообщества, а не только Google ([обзор](https://www.kubeflow.org/docs/components/pipelines/overview/), изменён 2026-06-13). Интерпретация: для нового проекта корректная формулировка - «TFX или KFP-совместимый пайплайн»; принципы важнее выбора инструмента.

### G-MLOPS-008 · SHOULD · Обучение оформлено оркестрованным пайплайном из модульных компонентов, и один и тот же пайплайн используется в разработке и в продакшене
- Проверка: в репозитории есть описание пайплайна (TFX, KFP; «не Google»: `dvc.yaml`); ручное ревью.
- Источник: [MLOps: Continuous delivery and automation pipelines in ML, уровень 1](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) (2024-08-28) · официальный гайд · высокая.

### G-MLOPS-009 · SHOULD · Определения пайплайнов и код обучения лежат в git, а образы компонентов собираются в CI и получают тег по SHA коммита
- Проверка: шаг CI «сборка образа с тегом = SHA коммита»; запрет тега `latest` в определениях пайплайна - ручное ревью или `grep`.
- Источник: [Best practices for implementing ML on Google Cloud](https://docs.cloud.google.com/architecture/ml-on-gcp-best-practices) (2024-09-09) · официальный гайд · высокая; [Architecture for MLOps using TFX, Pipelines and Cloud Build](https://docs.cloud.google.com/architecture/architecture-for-mlops-using-tfx-kubeflow-pipelines-and-cloud-build) (2024-06-28) · официальный гайд · высокая.

### G-MLOPS-010 · SHOULD · Каждый запуск пайплайна записывает метаданные: версии пайплайна и компонентов, параметры, указатели на входные и выходные артефакты, метрики оценки и указатель на предыдущую обученную модель
- Проверка: ручное ревью; наличие записи в хранилище метаданных (ML Metadata или аналог) для последнего запуска.
- Источник: [MLOps: Continuous delivery and automation pipelines in ML, уровень 1, управление метаданными](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) (2024-08-28) · официальный гайд · высокая; [TFX README](https://github.com/tensorflow/tfx/blob/master/README.md) (TFX 1.21.0) · конфиг или инструмент · высокая.

### G-MLOPS-011 · SHOULD · Код преобразования признаков общий для обучения и инференса
- Проверка: ручное ревью архитектуры: преобразования живут в одном модуле (в TFX - компонент Transform), который импортируют и обучение, и сервис; тест G-MLOPS-013 ловит расхождение.
- Источник: [Rules of ML, правило № 32](https://developers.google.com/machine-learning/guides/rules-of-ml#rule_32_re_use_code_between_your_training_pipeline_and_your_serving_pipeline_whenever_possible) (2025-08-25) · официальный гайд · высокая; [TFX guide](https://www.tensorflow.org/tfx/guide) (2024-09-06) · официальный гайд · высокая.
- Пример:

```python
# плохо: одна и та же нормализация написана дважды и со временем расходится
# train.py
x = (x - x.mean()) / x.std()
# server.py
x = (x - 0.5) / 0.25

# хорошо: один модуль, параметры преобразования - часть артефакта модели
# features.py
def normalize(x, stats):
    return (x - stats.mean) / stats.std
```

## 5. CI для ML: тесты данных и моделей

Три источника Google дают перечни проверок, и они почти совпадают: уровень 2 документа об MLOps, модуль «Production ML systems» курса ML Crash Course и группы «Features and Data» и «ML Infrastructure» рубрики ML Test Score. Правила ниже - их пересечение.

### G-MLOPS-012 · SHOULD · Ожидания к данным записаны в схеме, которая лежит в репозитории и проходит ревью; данные проверяются по ней до обучения и перед пакетным инференсом, а расхождение со схемой останавливает пайплайн
- Проверка: TFDV (`SchemaGen`, `ExampleValidator`) как шаг пайплайна или тест схемы в CI; автоматически выведенную схему человек просматривает и уточняет.
- Источник: [TFDV: Get started](https://www.tensorflow.org/tfx/data_validation/get_started) (2023-03-09) · официальный гайд · высокая; [The ML Test Score, тест Data 1](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (2017) · книга, статья или доклад · высокая.

Признаки, которых нет при обслуживании (например, метка), описываются в схеме TFDV через окружения `TRAINING` и `SERVING`, а не исключением из проверки.

### G-MLOPS-013 · SHOULD · Инфраструктура тестируется отдельно от ML: и подача данных в алгоритм, и совпадение предсказаний модели в обучении и после экспорта в окружение обслуживания
- Проверка: тесты в CI: один шаг обучения на случайных данных; круг «экспорт → загрузка → те же предсказания на фиксированных входах».
- Источник: [Rules of ML, правило № 5](https://developers.google.com/machine-learning/guides/rules-of-ml) (2025-08-25) · официальный гайд · высокая; [ML Crash Course: Deployment testing](https://developers.google.com/machine-learning/crash-course/production-ml-systems/deployment-testing) (2025) · официальный гайд · высокая.
- Пример:

```python
# хорошо: тест не проверяет качество, только механику экспорта
def test_export_roundtrip(tmp_path, model, sample_batch):
    expected = model(sample_batch)
    export_dir = tmp_path / "1"
    export_model(model, export_dir)
    restored = load_for_serving(export_dir)
    np.testing.assert_allclose(restored(sample_batch), expected, rtol=1e-5)
```

### G-MLOPS-014 · SHOULD · CI ML-проекта содержит юнит-тесты кода признаков и методов модели, проверку сходимости на малой выборке, проверку отсутствия NaN, проверку артефактов каждого компонента и интеграционный прогон пайплайна на малых данных
- Проверка: джобы CI; быстрые тесты - на каждый PR, интеграционный прогон - отдельным джобом.
- Источник: [MLOps: Continuous delivery and automation pipelines in ML, уровень 2](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) (2024-08-28) · официальный гайд · высокая; [The ML Test Score, тесты Data 7, Infra 2, Infra 3](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (2017) · книга, статья или доклад · высокая.

«Сходимость на малой выборке» означает, что модель способна переобучиться на нескольких примерах: это проверка механики обучения, а не качества. Тест воспроизводимости обучения (Infra 1) описан в [reproducibility.md](reproducibility.md).

### G-MLOPS-015 · SHOULD · Тестовая выборка берётся из периода после обучающей
- Проверка: тест на даты разбиения.
- Источник: [Rules of ML, правило № 33](https://developers.google.com/machine-learning/guides/rules-of-ml) (2025-08-25) · официальный гайд · высокая.
- Пример:

```python
# плохо: случайное разбиение смешивает прошлое и будущее
train, test = train_test_split(events, test_size=0.2, random_state=0)

# хорошо: модель на данных до 5 января проверяется на данных с 6 января
train = events[events["event_date"] <= "2026-01-05"]
test = events[events["event_date"] >= "2026-01-06"]
assert train["event_date"].max() < test["event_date"].min()
```

### G-MLOPS-016 · SHOULD · Порог решения вычисляется пайплайном на отложенных данных и сохраняется вместе с моделью, а не записывается константой в коде сервиса
- Проверка: ручное ревью; поиск числовых порогов в коде обслуживания.
- Источник: [Hidden Technical Debt in ML Systems, §7 «Fixed thresholds in dynamic systems»](https://proceedings.neurips.cc/paper_files/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf) (NIPS 2015) · книга, статья или доклад · высокая.
- Пример:

```python
# плохо: порог подобран под прошлую версию модели и устарел после переобучения
is_spam = score > 0.83

# хорошо: порог - артефакт того же запуска, что и веса
threshold = load_json(model_dir / "threshold.json")["value"]
is_spam = score > threshold
```

## 6. CD и готовность к продакшену

Документ об уровнях MLOps перечисляет проверки перед выкладкой: совместимость модели с целевой инфраструктурой (пакеты, память, ускорители), тест API сервиса ожидаемыми входами, нагрузочный тест (QPS, латентность), валидация данных для переобучения и пакетных предсказаний, достижение целевого качества. Продвижение по окружениям ступенчатое: автоматически в тестовое, после ревью в предпродакшен, вручную в продакшен после успешных прогонов в предпродакшене.

### G-MLOPS-017 · SHOULD · Перед выкладкой модель сравнивается с текущей версией или бейзлайном и с фиксированными порогами качества, в том числе на важных срезах данных
- Проверка: блокирующий джоб CD (в TFX - компонент Evaluator на TensorFlow Model Analysis).
- Источник: [ML Crash Course: Deployment testing, «Validate model quality before serving»](https://developers.google.com/machine-learning/crash-course/production-ml-systems/deployment-testing) (2025) · официальный гайд · высокая; [The ML Test Score, тесты Infra 4, Model 5, Model 6](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (2017) · книга, статья или доклад · высокая.

### G-MLOPS-018 · SHOULD · Перед выкладкой проверяется, что модель загружается и отвечает на запросы в песочнице с тем же серверным бинарём и той же конфигурацией, что в продакшене
- Проверка: блокирующий джоб CD с контейнером-песочницей (в TFX - InfraValidator, режимы `LOAD_ONLY` и `LOAD_AND_QUERY`).
- Источник: [TFX: InfraValidator](https://www.tensorflow.org/tfx/guide/infra_validator) (просмотрено 2026-10-09) · официальный гайд · высокая; [ML Crash Course: Deployment testing, «Validate model-infrastructure compatibility before serving»](https://developers.google.com/machine-learning/crash-course/production-ml-systems/deployment-testing) (2025) · официальный гайд · высокая.

В TFX это условие жёсткое: Pusher выкладывает модель, только если и Evaluator, и InfraValidator выдали «blessing». InfraValidator проверяет механику, а не правильность предсказаний, и работает только с форматом SavedModel и TensorFlow Serving. Интерпретация: «двойное благословение» - самая переносимая идея TFX; в обычном репозитории это два обязательных джоба перед продвижением версии в реестре.

### G-MLOPS-019 · SHOULD · Готовность ML-системы к продакшену оценивается по рубрике ML Test Score; таблица с баллами лежит в репозитории и пересчитывается перед каждым крупным релизом
- Проверка: наличие файла с 28 строками рубрики и итоговым баллом (например, `docs/ml-test-score.md`); ручное ревью.
- Источник: [The ML Test Score](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (IEEE Big Data 2017) · книга, статья или доклад · высокая · реконструкция (рубрика и подсчёт - из статьи; требование хранить таблицу в репозитории - решение профиля).

### 6.2. Подсчёт

1. За тест, выполненный вручную с документированным результатом, ставится 0,5 балла.
2. За тест, который система запускает автоматически и регулярно, ставится 1 балл.
3. Баллы складываются внутри каждой из четырёх групп.
4. Итоговый ML Test Score - минимум из четырёх сумм: он растёт, только когда подтягиваются все области.

Пример: Data - 3,5; Model - 2,0; Infra - 4,0; Monitor - 1,5. Итог - 1,5, и следующий шаг - мониторинг, а не ещё один тест инфраструктуры.

Шкала из статьи (пересказ):

| Балл | Что означает |
|---|---|
| 0 | скорее исследовательский проект, чем продакшен-система |
| (0; 1] | не совсем без тестов, но возможны серьёзные дыры в надёжности |
| (1; 2] | первый проход по продакшенизации, нужны дополнительные вложения |
| (2; 3] | разумно протестировано, но можно автоматизировать больше |
| (3; 5] | сильное автоматическое тестирование и мониторинг, подходит для критичных систем |
| больше 5 | исключительный уровень автоматизации |

Порог, с которого систему можно выпускать, статья не задаёт: это решение команды. Публичных данных о том, какой балл набирают системы самого Google сегодня, не найдено.

## 7. Реестр моделей, выкладка и откат

### G-MLOPS-020 · SHOULD · Модель попадает в продакшен только через реестр, где она зарегистрирована, проверена и одобрена, а сервис берёт её по идентификатору версии
- Проверка: ручное ревью процесса; в CD выкладка принимает только идентификатор версии из реестра, а не путь к файлу.
- Источник: [Practitioners guide to MLOps](https://services.google.com/fh/files/misc/practitioners_guide_to_mlops_whitepaper.pdf) (2021-05) · книга, статья или доклад · высокая; [Introduction to Model Registry](https://docs.cloud.google.com/vertex-ai/docs/model-registry/introduction) (просмотрено 2026-10-09) · официальный гайд · средняя.

Whitepaper описывает управление моделями как регистрацию, ревью, валидацию и одобрение перед выкладкой, а реестр - как место, где версию выпускают и откатывают. Без облака Google ту же роль выполняет реестр MLflow с версиями и алиасами ([Model Registry](https://mlflow.org/docs/latest/ml/model-registry/), не Google).

### G-MLOPS-021 · SHOULD · Новая версия модели выкатывается постепенно - канареечно или A/B на долю трафика, - а откат на предыдущую версию предусмотрен и проверен на практике
- Проверка: описание процедуры выкладки и отката в репозитории; периодическое учение по откату; ручное ревью.
- Источник: [The ML Test Score, тесты Infra 6 и Infra 7](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (2017) · книга, статья или доклад · высокая; [Architecture for MLOps using TFX, Pipelines and Cloud Build](https://docs.cloud.google.com/architecture/architecture-for-mlops-using-tfx-kubeflow-pipelines-and-cloud-build) (2024-06-28) · официальный гайд · высокая.

Архитектурный документ приводит числа: канареечная выкладка с наблюдением за CPU, памятью и диском, затем A/B-тест на 10-20 % трафика с возвратом к текущей модели при ухудшении. Whitepaper перечисляет стратегии: canary, blue-green, shadow, A/B, multi-armed bandit.

Отдельного публичного документа Google о процедуре отката нет - публичных данных не найдено. Откат упоминается в четырёх местах: тест Infra 7 рубрики ML Test Score, указатель на предыдущую модель в метаданных запуска (G-MLOPS-010), слово «roll back» в описании реестра в whitepaper и возврат к текущей модели в архитектурном документе. Минимальная процедура для своего проекта (реконструкция): предыдущая версия остаётся в реестре и в сервисе; откат - это переключение идентификатора версии, а не переобучение; после отката заводится разбор причин.

## 8. Мониторинг, skew и дрейф

Термины по whitepaper и документации TFDV:

| Термин | Смысл |
|---|---|
| Schema skew | обучающие данные и данные обслуживания не соответствуют одной схеме |
| Distribution skew | распределения признаков в обучении и в обслуживании различаются |
| Training-serving skew | расхождение между обучением и обслуживанием в целом: в данных, в коде преобразований, в поведении модели |
| Data drift | разрыв между обучающими и продакшен-данными растёт со временем |
| Concept drift | меняется связь между входными признаками и целевой переменной |
| Staleness | модель давно не переобучалась на свежих данных |

TFDV различает skew (обучение против обслуживания) и drift (соседние дни обучающих данных) и задаёт оба компараторами в схеме. Норма L-infinity ловит расхождение только для категориальных признаков; для числовых нужен порог `jensen_shannon_divergence`. Порог 0,01 в документации - пример, а не рекомендация: Google Cloud прямо советует настраивать пороги алертов под задачу.

### G-MLOPS-022 · SHOULD · В продакшене мониторятся инварианты входных данных, skew и drift, возраст модели, NaN и Inf, вычислительная производительность и качество предсказаний, и для каждого сигнала задан порог алерта
- Проверка: конфигурация алертов и дашбордов в репозитории; ручное ревью.
- Источник: [The ML Test Score, тесты Monitor 1-7](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf) (2017) · книга, статья или доклад · высокая; [Best practices for implementing ML on Google Cloud, рекомендации о skew, drift и порогах алертов](https://docs.cloud.google.com/architecture/ml-on-gcp-best-practices) (2024-09-09) · официальный гайд · высокая.

Уточнения из других источников. Rules of ML: знать требования к свежести (правило № 8) и следить за тихими отказами - устаревшей таблицей-источником, падением покрытия признака (правило № 10). ML Crash Course: отслеживать время с последнего переобучения и задать порог возраста для алерта. Google Cloud: если обучающие данные доступны, предпочтительна детекция skew, иначе - drift.

### G-MLOPS-023 · SHOULD · Training-serving skew измеряется, а признаки, использованные при обслуживании, записываются в лог и используются для обучения
- Проверка: сравнение статистик «обучающие данные - лог обслуживания» (в TFDV - `skew_comparator`) с алертом.
- Источник: [Rules of ML, правило № 37](https://developers.google.com/machine-learning/guides/rules-of-ml#rule_37_measure_training_serving_skew) (2025-08-25) · официальный гайд · высокая; [TFDV: Get started, раздел о skew и drift](https://www.tensorflow.org/tfx/data_validation/get_started) (2023-03-09) · официальный гайд · высокая. Запись признаков обслуживания в лог - правило № 29 того же гайда.
- Пример:

```python
import tensorflow_data_validation as tfdv

# хорошо: skew категориального признака проверяется на каждом запуске
tfdv.get_feature(schema, "payment_type").skew_comparator.infinity_norm.threshold = 0.01
anomalies = tfdv.validate_statistics(
    statistics=train_stats, schema=schema, serving_statistics=serving_stats)
```

### G-MLOPS-024 · SHOULD · У каждого признака есть владелец и описание; признаки, которыми модель больше не пользуется, удаляются
- Проверка: реестр признаков в репозитории (файл с полями «имя, источник, владелец, описание») и `CODEOWNERS`; ручное ревью.
- Источник: [Rules of ML, правила № 11 и № 22](https://developers.google.com/machine-learning/guides/rules-of-ml) (2025-08-25) · официальный гайд · высокая; [Hidden Technical Debt in ML Systems, §3 «Underutilized data dependencies»](https://proceedings.neurips.cc/paper_files/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf) (NIPS 2015) · книга, статья или доклад · высокая.

## 10. C++ в ML

Для C++-кода инференса и расширений действует общий Google C++ Style Guide (см. [cpp.md](../languages/cpp.md)). ML-специфичные добавки публично есть только у TensorFlow: два абзаца о возврате ошибок и правила написания custom ops. Публичного стайлгайда для C++-кода LiteRT и XLA не найдено - публичных данных не найдено. LiteRT (бывший TensorFlow Lite) предоставляет C++ API (цель CMake `litert_cc_api`) и принимает модели, сконвертированные из PyTorch, TensorFlow и JAX ([обзор](https://developers.google.com/edge/litert), 2026-09-25).

### G-MLOPS-027 · SHOULD · C++-код инференса и расширений подчиняется Google C++ Style Guide и форматируется `clang-format` со стилем Google
- Проверка: `clang-format` (`BasedOnStyle: Google`) и `clang-tidy` с конфигами профиля из `configs/cpp/`.
- Источник: [TensorFlow code style guide, раздел C++](https://www.tensorflow.org/community/contribute/code_style) (сайт 2021-04-08, файл 2024-07-24) · производный гайд проекта · высокая; [`.clang-format` TensorFlow](https://github.com/tensorflow/tensorflow/blob/master/.clang-format) (HEAD 2026-10) · конфиг или инструмент · высокая.

### G-MLOPS-028 · SHOULD · В C++-коде TensorFlow и его расширений функция, которая может завершиться ошибкой, возвращает `tensorflow::Status`, ошибка пробрасывается макросом `TF_RETURN_IF_ERROR`, а `StatusOr<T>` не используется
- Проверка: ручное ревью.
- Источник: [TensorFlow C++ Coding Style](https://github.com/tensorflow/community/blob/master/governance/cpp-style.md) (2020-05-04, не обновляется) · производный гайд проекта · средняя.
- Пример:

```cpp
// плохо: ошибка чтения теряется
void LoadVocabulary(const std::string& path, Vocabulary* vocab);

// хорошо
tensorflow::Status LoadVocabulary(const std::string& path, Vocabulary* vocab);

tensorflow::Status Init(const std::string& path, Vocabulary* vocab) {
  TF_RETURN_IF_ERROR(LoadVocabulary(path, vocab));
  return tensorflow::Status();
}
```

Правило относится к коду, который живёт в TensorFlow или расширяет его. Документ состоит из одного коммита 2020 года; для собственного сервиса инференса действуют общие правила обработки ошибок из [cpp.md](../languages/cpp.md).

### G-MLOPS-029 · MUST · Метод `Compute` ядра операции (`OpKernel`) потокобезопасен: разделяемое состояние в членах класса защищено мьютексом
- Проверка: ручное ревью; дополнительно - прогон тестов операции под ThreadSanitizer (`-fsanitize=thread`; предложение профиля, в источнике его нет).
- Источник: [Create an op](https://www.tensorflow.org/guide/create_op) (2024-01-31) · официальный гайд · высокая.

### G-MLOPS-030 · MUST · Изменение спецификации существующей операции не ломает ранее сериализованные `GraphDef`; несовместимое изменение оформляется как новая операция с новым именем
- Проверка: ручное ревью; тест загрузки графа, сохранённого предыдущей версией.
- Источник: [Create an op, раздел об обратной совместимости](https://www.tensorflow.org/guide/create_op) (2024-01-31) · официальный гайд · высокая.

### G-MLOPS-031 · SHOULD · Custom op пишется, только если операцию нельзя выразить композицией существующих; у него имя в CamelCase с префиксом проекта, проверка входов через `OP_REQUIRES`, сборка через `tf_custom_op_library` и тест на `tf.test.TestCase`
- Проверка: ручное ревью; тест операции в CI.
- Источник: [Create an op](https://www.tensorflow.org/guide/create_op) (2024-01-31) · официальный гайд · высокая; [tensorflow/custom-op](https://github.com/tensorflow/custom-op) (последний коммит 2021-03-18, не обновляется) · производный гайд проекта · средняя.

Загрузка SavedModel из C++ возвращает `SavedModelBundle` (граф и сессию) и требует указать теги графа ([SavedModel guide](https://www.tensorflow.org/guide/saved_model)). Модель из недоверенного источника загружать нельзя: SavedModel - исполняемый код (см. G-LIB-007).
