# Матрица «правило → инструмент / ручное ревью» (профиль Google)

> Данные актуальны на 2026-10-09.

В профиле 508 правил; инструмент проверяет целиком 168 (33 %), частично - 163 (32 %), только ручным ревью проверяются 177 (35 %). Для Python и C++ таблицы приведены полностью, для остальных областей - в сжатом виде. Строки таблиц сгенерированы скриптом из строк «Проверка» документов профиля (ничего не набрано вручную); класс проверки взят из того же индекса, по которому посчитаны числа в [README профиля](../README.md). Готовых CI-конвейеров и pre-commit-конфигов Google для обычного git не публикует: разделы о стадиях проверки - сборка профиля по тексту гайдов (не Google).

## 1. Как читать таблицы

| Класс | Значение |
|---|---|
| **инструмент** | строка «Проверка» правила называет инструмент (линтер, форматтер, флаг компилятора, настройку хостинга, тест в CI), который закрывает правило целиком |
| **частично** | строка начинается с «частично:» либо называет инструмент и «ручное ревью» вместе: инструмент ловит форму, смысл проверяет человек |
| **ревью** | только «ручное ревью» (иногда с подсказкой, что искать) |

- Уровень: `MUST` - формулировка источника обязательна или правило навязано форматтером / CI проекта-источника; `SHOULD` - рекомендация или реконструкция из практики. Подробности - в строке «Источник» каждого правила.
- Инструменты, которые назвал сам Google (pyink или Black, pylint с `pylintrc`, clang-format с `BasedOnStyle: Google`, google-java-format, Error Prone, gofmt, addlicense, gem `google-style`), в документах не помечены; всё остальное (ruff, mypy, isort, clang-tidy, cpplint-форк, Prettier, ESLint-плагины, Stylelint, commitlint, pre-commit, nbstripout, jupytext, gitleaks, markdownlint, Scorecard и др.) - «не Google», это сказано в строках «Проверка» и в [README профиля](../README.md).
- Ссылка в столбце ID ведёт на документ с полным текстом правила, источником и примером.
- Коды проверок соответствуют версиям инструментов из [configs/](../configs/): ruff 0.16.8, pylint 4.1.2 (Google `pylintrc`, 2025-02-21), mypy 2.3.1, pyink 26.5.1, isort 9.0.2, clang-format и clang-tidy 18.1.3, cpplint 2.0.2, ESLint 10.12.0 с typescript-eslint 8.71.1 и angular-eslint 22.5.0, Prettier 3.9.9, Stylelint 17.16.0, commitlint 21.2.3.

## 3. Стадии проверки: редактор → pre-commit → CI → ревью

Google не публикует ни pre-commit-конфига, ни эталонного workflow для обычного git: внутри компании форматирование и линтеры запускает presubmit монорепозитория, а ревью идёт в Critique. Ни один из 24 измеренных открытых репозиториев Google не запускает clang-format или clang-tidy в GitHub Actions; `.pre-commit-config.yaml` есть у 6 из 24, `.editorconfig` - у 4 из 24 (измерение - в [research/google.md](../research/google.md)). Поэтому разбивка ниже - конструкция профиля по тексту гайдов (не Google), а файлы, которые её реализуют, лежат в [configs/](../configs/) и [templates/](../templates/).

| Стадия | Файл профиля | Что ловит | Правила (примеры) |
|---|---|---|---|
| Редактор | [configs/.editorconfig](../configs/.editorconfig) | отступы, табы, кодировка, конец строки, подсказка о ширине строки - до того как код попал в git | G-PY-002, G-PY-004, G-PY-005, G-CPP-001, G-CPP-002, G-CPP-008, G-TS-003, G-JAVA-001, G-KT-001, G-GO-001, G-CS-001, G-DOC-006 |

Правила разбивки:

- Один инструмент - одна версия на всех стадиях: pre-commit, CI и редактор используют те же `.clang-format`, `pyproject.toml`, `eslint.config.js`, что лежат в [configs/](../configs/). Версии закреплены в `rev:` хуков и в командах установки CI и совпадают с шапками конфигов.
- pre-commit - удобство, CI - граница: на сервере проверяется всё дерево (`pre-commit run --all-files` либо прямые команды), и именно статусы `lint` и `test` делаются обязательными для слияния (G-REPO-022, G-BR-011). Так делают 5 из 6 репозиториев Google с pre-commit-конфигом.
- Медленное - только в CI: clang-tidy нужен `compile_commands.json`, mypy и pylint - установленные зависимости, типизированному ESLint - `npm ci`. В pre-commit этих хуков нет (clang-tidy) или они работают в изолированном окружении без зависимостей проекта (pylint из репозитория pylint-dev - отчёт беднее, но не ломается, потому что Google `pylintrc` отключает `import-error` и `no-member`).
- Сторонний код исключён везде одинаково: `third_party/` не форматируется, не линтуется и не получает заголовков лицензии (G-REPO-015); исключения прописаны в каждом конфиге, хуке и команде.
- Проверка сообщений коммитов идёт на стадии `commit-msg` локально и по заголовку PR / MR в CI: при обязательном squash-слиянии в историю попадает именно заголовок PR (G-GIT-015).

## 7. Что остаётся на ревью и почему

Автоматизировать удалось форму; то, что требует понимания задачи, остаётся за ревьюером. Ниже - группы правил класса «ревью» и причина, по которой для них нет инструмента (или он намеренно не включён).

| Группа | Правила (примеры) | Почему без инструмента |
|---|---|---|
| Имена по смыслу, а не по форме | G-PY-015, G-PY-016, G-CPP-009, G-NG-006 | линтер проверяет регистр и суффиксы (`readability-identifier-naming`, `ruff N*`), но не то, что имя описывает назначение; «односимвольное имя только для счётчика», «описательное имя `TypeVar`», запрет «общих» имён файлов (`utils.ts`) формализовать нельзя |
| Комментарии и докстринги по содержанию | G-PY-029, G-PY-032, G-PY-038, G-CPP-030, G-CPP-033 | `ruff D*` с `convention = "google"` проверяет наличие и разметку секций, а не то, что докстринг описывает контракт, сообщение об ошибке называет условие, а язык комментариев инклюзивный |
| Структура модулей и API | G-PY-017, G-PY-019, G-PY-023, G-PY-024, G-PY-025, G-CPP-026, G-CPP-027, G-CPP-047, G-CPP-048, G-CPP-050, G-NG-011 | «импортируйте модули, а не имена», «не прячьте импорты под `TYPE_CHECKING`», «`struct` - только пассивные данные», «результат значением, а не выходным параметром» - семантические решения; `ruff ICN001` и `TC001-TC003` требуют обратного гайду и выключены |
| Запрещённые возможности языка в «серой зоне» | G-PY-037, G-PY-049, G-PY-050, G-PY-053, G-PY-055, G-PY-057, G-PY-058, G-CPP-045, G-CPP-054, G-CPP-057, G-CPP-065 | гайд запрещает не конструкцию, а её применение сверх меры (`assert` вместо проверки аргумента, вложенные comprehension, лишние свойства, `auto` там, где он прячет тип, RTTI «кроме тестов», макросы «кроме крайних случаев») - порог определяет человек; `ruff S101` флагует любой `assert` и поэтому не включён |
| Процесс: описание изменения, тон ревью, размер PR | G-GIT-001, G-GIT-002, G-GIT-006, G-GIT-012, G-CR-002…004, G-CR-007…015, G-CR-018, G-BR-004, G-BR-008, G-BR-012 | commitlint проверяет длину и форму заголовка, но не «что и почему»; 13 из 18 правил ревью у Google выполняют люди - это суть Code Review Developer Guide |
| Архитектура ML-системы | G-ML-001, G-ML-005, G-ML-006, G-ML-013, G-REPRO-009, G-REPRO-016, G-MLOPS-001, G-MLOPS-006, G-MLOPS-020, G-LIB-001, G-LIB-016, G-LIB-018 | «простая модель сначала», «версия данных вместо latest», «модель в продакшен только через реестр», «функционально чистая функция под `jit`» - свойства системы, а не файла; их ловят тесты (G-MLOPS-013, G-REPRO-011) и ревью, а не линтер |
| Юридическое и организационное | G-REPO-008, G-REPO-011, G-REPO-012, G-REPO-018, G-REPO-023, G-REL-007, G-REL-012 | выбор правообладателя, года в заголовке, статуса поддержки и срока поддержки версии - решения владельца проекта; инструмент проверяет только наличие строки (`addlicense -check`) |

Как профиль помогает ревьюеру: в шаблоне PR / MR ([templates/github/PULL_REQUEST_TEMPLATE.md](../templates/github/PULL_REQUEST_TEMPLATE.md), [templates/gitlab/merge_request_templates/Default.md](../templates/gitlab/merge_request_templates/Default.md)) есть чек-лист, в [git/code-review.md](git/code-review.md) - порядок просмотра и метки серьёзности замечаний (G-CR-007), а ID правил можно ставить прямо в комментарии ревью («G-PY-017: импортируйте модуль, не функцию»).

## 8. Ограничения и что не проверено

- Класс «инструмент» означает «правило выразимо проверкой из конфигов профиля», а не «проверка запускалась здесь». Локально запущены: ruff 0.16.8, mypy 2.3.1, pytest 9.1.1, pyright 1.1.414, clang-format и clang-tidy 18.1.3, clang++ 18.1.3, gofmt и go vet (Go 1.24.7), rustfmt 1.9.0 и clippy, Prettier 3.8.1, ESLint 10.1.0 с заглушками плагинов, PyYAML для разбора YAML. Не запускались (реестры пакетов недоступны из среды сборки): pyink, isort, pylint, cpplint, pre-commit, commitlint, nbstripout, jupytext, gitleaks, addlicense, google-java-format, ktfmt, dotnet format, PHP-CS-Fixer, RuboCop, Stylelint, настоящие плагины ESLint. Для них имена опций и кодов сверены с исходниками и документацией инструментов (подробности - в шапках конфигов и в [research/google.md](../research/google.md)).
- `addlicense -check` проверяет только наличие слов `copyright`, `mozilla public` или `spdx-license-identifier` в первых 1000 байтах файла: текст, год и правообладателя заголовка он не сверяет (G-REPO-010, G-REPO-013 - «частично»).
- Настройки хостинга (защита ветки, обязательные одобрения, владельцы кода) на GitLab Free частично недоступны: «Required approvals» и «Require approval from code owners» - только в Premium и Ultimate. Для GitLab Free правила G-CR-001 и G-CR-016 выполняются организационно (см. [adoption.md](adoption.md)).
- Правила, помеченные в документах «реконструкция» или «практика, выведенная из репозиториев», проверяются так же, как остальные, но их обязательность ниже: это не письменное правило Google.
- Матрица пересчитывается скриптом из документов профиля; при добавлении правила (новый номер в конце области, ID не переиспользуются) достаточно перегенерировать файл.
