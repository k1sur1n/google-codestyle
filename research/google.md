# Google: исследование правил оформления кода, git-репозиториев и ML-проектов (разделы A-F)

> Данные актуальны на 2026-10-09.

У Google есть единая витрина публичных стайлгайдов - google/styleguide - но это не один документ, а 17 отдельных гайдов по языкам со своими владельцами, которые экспортируются из внутренних версий нерегулярно и без приёма внешних правок. Текст гайдов живее, чем инструменты к ним: за 2024-2026 годы Google удалил cpplint из репозитория, заархивировал eslint-config-google и pytype, перестал развивать yapf, поэтому профиль Google в этом репозитории опирается на текст гайдов как на источник истины, а конфиги строит на живых инструментах - clang-format и clang-tidy из LLVM, pyink, ruff и mypy - с перечнем известных расхождений. Правила для git-репозиториев у Google письменные (документация OSPO, eng-practices, docguide), но практика 24 измеренных репозиториев делится пополам: 12 - односторонний экспорт из монорепозитория через Copybara, 12 ведутся на GitHub и живут по конвенциям сообщества (Conventional Commits, SemVer, squash). Внутренние практики - Piper, Critique, readability, TAP, LSC - описаны в книге «Software Engineering at Google» (2020) и статьях 2016-2018 годов; на обычный git-репозиторий переносятся малые изменения, стандарт ревью, владельцы кода, обязательные форматтеры и trunk-based development, а не readability, LSC и глобальный TAP. По ML у Google есть живые принципы 2015-2017 годов, но нет гайда по оформлению ML-кода: раскладка проекта, выбор библиотеки конфигурации и работа с ноутбуками восстановлены по практике репозиториев и помечены как реконструкция.

Отчёт по Яндексу - [yandex.md](https://github.com/k1sur1n/yandex-codestyle/blob/main/research/yandex.md); сравнение двух подходов - [../comparison/README.md](../comparison/README.md). Профиль Google, на правила которого ссылается этот отчёт по ID вида `G-PY-012`, лежит в [`../`](../README.md).

## Метод и ограничения

**Первоисточники.** Гайды читались не с сайта, а из полного клона `google/styleguide` (ветка `gh-pages`, HEAD `d9e89d7` от 2026-10-07): так видна история каждого файла, автор экспорта и дата содержательного изменения отдельно от технических правок (разметка, пробелы в заголовках, миграция HTML → Markdown в сентябре-октябре 2026 года). Так же прочитаны `google/eng-practices`, `abseil/abseil.github.io` (HTML книги «Software Engineering at Google», далее - SWE; якоря взяты из атрибутов `id`), репозитории инструментов (pyink, yapf, pytype, gts, eslint-config-google, addlicense, release-please, cpplint/cpplint, typescript-eslint, angular-eslint, Stylelint, jax, flax, tensorflow/docs и другие). Страницы вне GitHub - opensource.google, developers.google.com, docs.cloud.google.com, angular.dev, docs.jax.dev, keras.io, abseil.io - открывались напрямую; у части из них извлечены только текст и дата, без якорей. Полный текст статьи CACM 2016 о монорепозитории получить не удалось: её цифры подтверждены через статью Фергуса Хендерсона (arXiv, 2017), сноски SWE и дословные выдержки у сторонних авторов, и это оговорено при каждой цифре в разделе D.

**Измерение репозиториев.** Практика оформления git-репозиториев измерена 2026-10-09 по **24 репозиториям** из десяти организаций (`google`, `googleapis`, `GoogleCloudPlatform`, `abseil`, `bazelbuild`, `tensorflow`, `keras-team`, `jax-ml`, `google-deepmind`, `google-research`) и шаблону `google/new-project` как эталону - всего 25 клонов: abseil-cpp, abseil-py, bazel, flatbuffers, flax, go-github, googletest, gts, guava, leveldb, pyink, python-fire, re2, yapf, optax, google-research, google-cloud-go, google-cloud-python, release-please, microservices-demo, python-docs-samples, jax, keras, tensorflow. Репозитории клонировались командой `git clone --depth 400 --filter=blob:none --sparse`, файлы читались из `HEAD`, ветки и теги снимались через `git ls-remote`. Из каждого репозитория взято до 300 последних коммитов - **7 006 сообщений** (с шаблоном - 7 041; у pyink всего 106 коммитов, у шаблона - 35). 22 репозитория из 24 имеют коммиты 2026 года, yapf и python-fire - нет; доли в отчёте даны для N = 24. Для заголовков лицензии взято по 10 случайных исходных файлов на репозиторий - 240 файлов. Отдельные pull request через API не выгружались: API GitHub из среды измерения недоступен, поэтому число ревьюеров и время до слияния не измерялись, число PR оценено по суффиксу `(#N)` в сообщениях (2 976 коммитов), а настройки защиты веток видны только там, где лежат в репозитории как код - в 3 из 24. Внутри той же выборки по языкам: 12 Python-репозиториев (flax, optax, jax, keras, tensorflow, abseil-py, pyink, yapf, python-fire, google-cloud-python, python-docs-samples, google-research) и 6 C++-репозиториев (abseil-cpp, googletest, leveldb, re2, flatbuffers, tensorflow). Для ML дополнительно просмотрены chex, orbax и tfx (вне 24), 14 каталогов `examples/` во Flax (коммит `6c9494b`, 2026-10-07) и 755 проектов монорепозитория google-research (коммит `72ffe35`, 2026-10-08).

**Gerrit.** Страницы журнала на `go.googlesource.com`, `chromium.googlesource.com` и `android.googlesource.com` закрыты для роботов, поэтому история трёх проектов взята с зеркал на GitHub - golang/go (две выборки: 40 и 300 коммитов), chromium/chromium (60), aosp-mirror/platform_frameworks_base (60; публичная ветка `main` не обновлялась с 2025-03-26) - а отдельные коммиты сверены на самих хостах. По той же причине не получены даты правок файлов стайлгайда Chromium: Gitiles не отдаёт историю автоматическому чтению.

**Локальная проверка инструментов.** В среде сборки были clang-format и clang-tidy 18.1.3, ruff 0.16.8, Black 26.5.1, mypy 2.3.1, pyright 1.1.414, ESLint 10.1.0 и Prettier 3.8.1 (без плагинов), Python 3.13, uv 0.11.32, git-lfs 3.4.1; реестры npm и PyPI недоступны. Поэтому конфиги профиля проверены запуском только на этих версиях: `.clang-format` и `.clang-tidy` - на LLVM 18.1.3, секции ruff, mypy и pytest в `pyproject.toml` - запуском, `eslint.config.js` - загрузкой с заглушками плагинов. Не запускались: pyink, isort, pylint, cpplint, commitlint, pre-commit, Stylelint, nbstripout, jupytext, release-please, angular-eslint и typescript-eslint; их опции сверены с исходниками клонов. Утверждения о поведении clang-format 21-23 и clang-tidy 22-23 взяты из Release Notes и исходников LLVM.

**Что считается письменным правилом, а что практикой.** Письменное правило - текст официального гайда, документации OSPO, eng-practices или документации библиотеки Google; производный гайд проекта (Chromium, AOSP, Fuchsia, Flutter, TensorFlow) - тоже письменный источник, но помеченный отдельно; конфиг или инструмент - машиночитаемый файл или программа. Всё, что получено подсчётом по репозиториям, названо «практика, выведенная из репозиториев» с выборкой и долей («12 из 24»); правило, которого в письменных источниках нет и которое профиль синтезировал сам, помечено «реконструкция». Гайды Google не пользуются RFC 2119 и формально объявляют обязательным всё; уровни MUST и SHOULD в профиле - разметка по модальности формулировок (must / never / always → MUST; should / prefer / avoid → SHOULD) и по тому, проверяет ли правило форматтер или CI проекта-источника. Сами гайды распространяются под CC-BY 3.0, документация OSPO и developers.google.com - под CC BY 4.0, книга SWE - под CC BY-NC-ND 4.0: она в отчёте только пересказывается.

**Даты.** У коммитов google/styleguide дата автора и дата попадания в ветку часто различаются на месяцы: удаление cpplint (`3e13205`) написано 2024-07-08, а в ветку попало 2025-01-17; замена `LICENSE` на CC-BY-3.0 (`9002f62`) - 2024-07-09 и 2025-02-18. В отчёте используются даты автора, как в проверенных централизованно фактах; там, где заметки исследования приводили дату коммиттера, в тексте стоит дата автора, а расхождение названо один раз здесь.

**Что проверить не удалось.** Лицензии страниц LLVM, abseil.io, fuchsia.dev, source.android.com, protobuf.dev, bazel.build, go.dev, GitHub Docs, GitLab Docs и ряда сторонних инструментов - в карте источников стоит «лицензия не проверена». Тела продуктовых страниц Vertex AI (Experiments, Model Registry, Model Monitoring) не получены. Полные тексты статей CACM 2016 и ICSE-SEIP 2018 (опрос о монорепозитории) не открывались. Актуальных (после 2020 года) официальных цифр о монорепозитории, Critique, Tricorder и TAP не найдено - всё в разделе D относится к 2015-2019 годам. Чем заменён pytype внутри Google, какие проверки clang-tidy обязательны внутри компании, как устроен конвейер экспорта гайдов - публичных данных не найдено.

## A. Карта источников

Карта объединяет источники всех областей; строки, которые встречались в нескольких фрагментах исследования, сведены в одну. Состояние на 2026-10-09; HEAD google/styleguide - `d9e89d7` (2026-10-07). «Последнее содержательное изменение» отделено от технических правок (разметка, favicon, пробелы в заголовках). Типы источников - те же, что в профиле: `официальный гайд`, `производный гайд проекта`, `конфиг или инструмент`, `практика, выведенная из репозиториев`, `книга, статья или доклад`, `сторонний источник`; пометка «не Google» стоит там, где владелец источника - не Google, «архив» - у заархивированных.

**Как публикуется google/styleguide.** README называет гайды копиями внутренних: правки сначала вносятся внутри Google и лишь потом переносятся наружу, внешние вклады не принимаются, а шаблон pull request предупреждает, что существенные изменения должны быть предложены и одобрены на внутренних форумах и что непрошеные PR закрываются без комментария ([README](https://github.com/google/styleguide/blob/gh-pages/README.md), [PULL_REQUEST_TEMPLATE.md](https://github.com/google/styleguide/blob/gh-pages/.github/PULL_REQUEST_TEMPLATE.md)). Эта формулировка появилась 2021-04-08 ([`52483ac`](https://github.com/google/styleguide/commit/52483ac)); с тех пор модель не менялась. Issues при этом открыты, и в истории есть единичные принятые мелкие правки - замена формулировок в JS-гайде 2025-04-24 ([`f58fbef`](https://github.com/google/styleguide/commit/f58fbef)), исправление отступа в `pylintrc` в феврале 2025 года. Механизм синхронизации - смесь: Copybara-импорты от «Google Python team» (первый - 2017-12-19, [`54cca78`](https://github.com/google/styleguide/commit/54cca78)) для Python и Shell, ручные коммиты «Export the latest version of internal guide» для Go и «Update C++ style guide» для C++; ритм у каждого гайда свой. Публикация идёт с 2008 года: сначала через Google Code (svn), с 2015-05-20 - через GitHub ([`51ce2f4`](https://github.com/google/styleguide/commit/51ce2f4)); всего в ветке `gh-pages` 625 коммитов за 2008-2026 годы. Осенью 2026 года репозиторий пережил заметную чистку силами одного сопровождающего: перевод XML, JSON, Vim и Lisp в Markdown, экспорт свежих внутренних версий Shell, Lisp, Objective-C, R, Python, Java и HTML, первый экспорт Haskell и удаление старых гайдов ES5 и AngularJS ([история](https://github.com/google/styleguide/commits/gh-pages)). Интерпретация: это разовое наведение порядка, а не смена модели управления.

**Чего в карте нет.** Даты правок файлов Chromium не получены. Лицензии страниц source.android.com, fuchsia.dev, protobuf.dev, bazel.build, go.dev, LLVM, abseil.io и ряда сторонних сайтов не проверялись. Тела страниц Vertex AI Experiments, Model Registry и Model Monitoring не получены. Полные тексты статей CACM 2016 и ICSE-SEIP 2018 (опрос) не открывались; статистика из них дана по статье Хендерсона и сторонним выдержкам.

## B. Исходный код

### B.1. C++

**Что покрывает публичный гайд.** Google C++ Style Guide - один файл с разделами о заголовках, областях видимости, классах, функциях, «прочих возможностях C++», именовании, комментариях и форматировании. Это не свод правил оформления, а в первую очередь перечень языковых ограничений: целевой стандарт - **C++20 без возможностей C++23** ([C++ Version](https://google.github.io/styleguide/cppguide.html#C++_Version)), исключения не используются ([Exceptions](https://google.github.io/styleguide/cppguide.html#Exceptions)), запрещены модули C++20, корутины, пользовательские литералы (включая стандартные `5s` и `"x"sv`), заголовки `<ratio>`, `<cfenv>` и `<filesystem>`, `long double`, статические объекты с нетривиальным деструктором и объявление вперёд чужих сущностей. Раздела о Boost больше нет: 2026-05-01 его заменил раздел о сторонних библиотеках с приоритетом Abseil. Гайд формально называет все свои соглашения обязательными и не пользуется RFC 2119, поэтому уровни MUST и SHOULD в профиле - разметка по модальности формулировок: 45 правил MUST, 28 - SHOULD. В профиль отобрано 73 правила: [G-CPP-001 … G-CPP-073](../docs/languages/cpp.md).

**Чего в гайде мало.** О тестах сказано три вещи: имя файла `foo_test.cc`, разрешение на `protected`-поля фикстуры и свободный RTTI в тестах ([G-CPP-071](../docs/languages/cpp.md)). Остальное задают документация GoogleTest и две проверки clang-tidy (G-CPP-070, G-CPP-072). Отдельного раздела о логировании нет: тема сведена к совету брать библиотеку логирования вместо `std::cerr` (G-CPP-038). Обработка ошибок без исключений в гайде не расписана; `absl::Status` и `absl::StatusOr<T>` описаны в документации Abseil ([Status Guide](https://abseil.io/docs/cpp/guides/status); G-CPP-035). Для имён каталогов отдельного правила нет. Оценок `<ranges>`, `std::format`, `std::span` и списка разрешённых возможностей C++23 в публичных источниках не найдено.

**Темп изменений за 2023-2026 годы.** Гайд живой: с октября 2023 года - 9 содержательных обновлений с осмысленными описаниями коммитов ([история файла](https://github.com/google/styleguide/commits/gh-pages/cppguide.html)). Главные: переход на C++20 с концептами и `constinit` (2023-10-12, `901474a`); запрет `long double`, модулей и корутин (2024-09-05, `8c4da23`); обязательное `T* p` без пробела перед `*` (2025-07-31, `c6f57a9`); запрет объявлять вперёд чужие сущности и замена раздела Boost (2026-05-01, `3c5c895`); формулировка «разрешено, но не поощряется» для операторов без фигурных скобок (2026-05-07, `1809c76`); перевод исходника с HTML на Markdown (2026-09-29, `428b08a`). Последний коммит без объявления вернул раздел TODO от формы `// TODO: bug 12345 - …` к скобочной `// TODO(bug 12345): …` - вероятно, побочный эффект миграции (уверенность средняя). Полная таблица изменений - в разделе 8 [cpp.md](../docs/languages/cpp.md).

**Инструменты: кто официальный и кто соответствует гайду.**

- **clang-format, `BasedOnStyle: Google`.** Не продукт Google: пресет встроен в LLVM, его правят в том числе инженеры Google. Гайд упоминает clang-format один раз. Пресет поддерживается и почти полностью покрывает раздел о форматировании, но до версии 20 включительно расходился с гайдом в положении `*` и `&`: `DerivePointerAlignment: true` подражал стилю файла. Исправлено в 21.1.0 ([коммит LLVM](https://llvm.googlesource.com/llvm-project/+/9281797a577b7954521fb9192d41e457ca2ca42e) от 2025-07-25, за шесть дней до публикации правила в гайде). В выборке репозиториев `.clang-format` с `BasedOnStyle: Google` есть в 5 из 6 C++-проектов Google; других базовых стилей нет.
- **clang-tidy, семейство `google-*`.** Тоже часть LLVM, в гайде не упоминается. В документации 24.0.0git - 20 проверок: 16 для C++ и GoogleTest и 4 для Objective-C; в 18.1.3 - 19. Проверок именования для C++ среди них нет: имена проверяет `readability-identifier-naming` с ручной настройкой, то есть «Google-пресета» для clang-tidy не существует. В 22.1.0 появилась `google-runtime-float`, а `google-readability-todo` стала принимать форму TODO с дефисом; в 23.1.0 `google-explicit-constructor` стала алиасом `misc-explicit-constructor`. В выборке `.clang-tidy` есть в 1 из 6 C++-репозиториев, и ни один workflow из 24 репозиториев не запускает ни clang-format, ни clang-tidy: проверки идут вне GitHub. Какие проверки обязательны внутри Google - публичных данных не найдено.
- **cpplint.** Гайд по-прежнему советует `cpplint.py` ([раздел cpplint](https://google.github.io/styleguide/cppguide.html#cpplint)), но Google убрал его из `google/styleguide` 2024-07-08 и отправляет к форку сообщества. Форк поддерживается (2.0.2 от 2025-04-08), с текущим гайдом расходится в трёх местах (см. раздел E). В 25 репозиториях выборки cpplint не упоминается.
- **Abseil и GoogleTest.** Официальные библиотеки Google, обе активны. Abseil - первая в списке предпочтений гайда и источник API, которые гайд называет прямо (`absl::down_cast`, `absl::StrCat`, `absl::Status`). C++ Tips of the Week - публикуемая выборочно серия внутренних заметок; текущая редакция гайда ссылается на восемь из них (#42, #109, #116, #130, #140, #148, #176, #232).

**Конфиги профиля.** [`.clang-format`](../configs/cpp/.clang-format) - пресет плюс явные `DerivePointerAlignment: false`, `PointerAlignment: Left` и `Standard: c++20`. [`.clang-tidy`](../configs/cpp/.clang-tidy) - `google-*` без Objective-C, две проверки `abseil-*`, 14 поимённо выбранных проверок других семейств и настройки `readability-identifier-naming`. Оба файла проверены на LLVM 18.1.3: `--dump-config` и `--verify-config` проходят, образцы в стиле гайда дают 0 замечаний, образец с нарушениями - 55 замечаний от 24 проверок. На версиях 21-23 конфиги не запускались.

**Производные гайды.** Chromium и Fuchsia объявляют, что следуют публичному гайду, кроме перечисленных исключений, но расходятся в заметных параметрах: Chromium целится в C++23 (по состоянию на 01/2026), запрещает `std::function`, `std::shared_ptr`, `<chrono>` и большую часть Abseil, предпочитает объявления вперёд, требует `{}` везде и форматирует пресетом `Chromium`; Fuchsia берёт 100 колонок и запрещает вложенные namespace. Отдельного C++-гайда AOSP в изученных источниках нет - публичных данных не найдено; в AOSP есть только хуки `clang_format` и `cpplint` в repohooks. Сводная таблица - в разделе B.5 и в разделе 11 `cpp.md`.

### B.2. Python, Django, FastAPI

**Что публично существует по Python.** У Google один публичный документ о стиле Python - [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html) - и один машиночитаемый конфиг к нему, [`pylintrc`](https://google.github.io/styleguide/pylintrc). Гайд живой: за три года в него внесено пять содержательных обновлений, последнее - **2026-09-10**. Гайд состоит из двух частей: «правила языка» (какие конструкции разрешены) и «правила стиля» (как оформлять). Минимальную версию Python он не называет; по примерам видно, что рассчитан он на 3.10-3.12 (`X | None`, `typing.Self`, `typing.override`). Синтаксис PEP 695, оператор `match` и работа с `dataclasses` в гайде не описаны - публичных данных не найдено. Правила профиля: [G-PY-001 … G-PY-065](../docs/languages/python.md) (38 MUST, 27 SHOULD).

**Что изменилось за 2023-2026 годы.** Все изменения приближают гайд к PEP 8, Black и современной типизации. В 2023 году введён формат `TODO` со ссылкой вместо имени автора (G-PY-034), гайд стал упоминать Pyink вместо yapf (2023-02-16, [`e065b55`](https://github.com/google/styleguide/commit/e065b55)) и появился `@override` как условие, при котором переопределённому методу не нужен докстринг (G-PY-030). В 2024 году переписано правило об `assert` (G-PY-037). В 2025 году гайд стал предпочитать абстрактные контейнеры в аннотациях (G-PY-044), а `pylintrc` перешёл с отступа 2 на 4 пробела. В сентябре 2026 года в разделе об именах появилась прямая отсылка к PEP 8 (G-PY-011), из исключений импорта убран `six.moves` (G-PY-017), добавлено правило о докстрингах декорированных функций (G-PY-032). Сообщения коммитов безличны («Project import generated by Copybara»), мотивы изменений не объясняются.

**Формат докстринга.** Это то, что обычно называют «Google style»: строка-резюме не длиннее 80 символов, пустая строка, описание, секции `Args:`, `Returns:` (или `Yields:`), `Raises:`; у класса - `Attributes:`. Докстринг обязателен для публичных, нетривиальных и неочевидных функций (G-PY-027 … G-PY-032). Собственный `pylintrc` Google наличие докстрингов функций не проверяет; формат проверяет только ruff с `convention = "google"` - инструмент «не Google».

**Импорты.** Три правила отличают гайд от привычного Python: импортировать только модули и пакеты, но не классы и функции (G-PY-017); не использовать относительные импорты (G-PY-018); сортировать импорты по полному пути модуля, не разделяя `import x` и `from x import y` (G-PY-022). Публичной проверки первого правила нет: гайд упоминает внутренние проверки pylint с префиксом `g-`, но они не опубликованы.

**Типы и проверка типов.** Гайд «настоятельно рекомендует» аннотации и требует как минимум аннотировать публичные API (G-PY-042). Инструментом проверки он по-прежнему называет **pytype, хотя репозиторий pytype в архиве с 2026-09-03**, а последняя поддерживаемая им версия Python - 3.12 ([README](https://github.com/google/pytype/blob/main/README.md), [FAQ](https://github.com/google/pytype/issues/1925)). Чем pytype заменён внутри Google, публично не объявлено. В открытых репозиториях видны mypy (4 из 12), pytype (2), pyrefly (2), ty (1); в октябре 2026 года в abseil-py и flax появились экспортированные коммиты, которые заменяют подавления pytype на подавления pyrefly (признак внутренней миграции, уверенность средняя). Профиль использует mypy с пометкой «не Google»: он назван в FAQ pytype как зрелая альтернатива и чаще других встречается в репозиториях Google; pyright дан альтернативой.

**Форматтеры: pyink, yapf, Black.** Гайд называет Black и Pyink на равных и опирается на их поведение (хвостовая запятая, разрешение превысить 80 символов, если форматтер не справился). [pyink](https://github.com/google/pyink) - форк Black, который Google ведёт как «помощник при переходе» на Black; он активен, версии повторяют версии Black. Готового Google-пресета у pyink нет: по умолчанию 88 колонок, как у Black, поэтому 80 задаётся явно. От Black pyink отличают опция отступа в 2 пробела, выбор кавычек «по большинству в файле» и отказ переносить длинные импорты и строки с прагмами. [yapf](https://github.com/google/yapf) принадлежит Google, но гайд перестал его упоминать в 2023 году, релизов нет с ноября 2024 года, синтаксис Python 3.12 он не понимает - для нового кода не подходит. Практика 12 репозиториев: pyink настроен в 3 и ни в одном не проверяется в CI; yapf - 2, `ruff format` - 2, Black - 1, без форматтера - 5; при этом 8 из 12 отформатированы с отступом в 2 пробела (внутренний стиль Google), Keras - с 4; pytest упомянут в конфиге или CI у 9 из 12, `filterwarnings = ["error", …]` - у 4.

**Статус `pylintrc`.** Файл официальный и поддерживается (последняя правка - 2025-02-21), но сам называет себя «best-effort» и текст гайда покрывает не полностью: в списке `disable=` - категория `R` и ещё 78 сообщений, в том числе проверки докстрингов функций, порядка импортов и формата `TODO`; регулярные выражения допускают `CamelCase` для функций; с 2025-02-18 у файла собственный заголовок Apache-2.0. Как pylint 4.1.2 работает с этим файлом, запуском не проверено: в среде сборки pylint недоступен.

**Конфиги.** [`pyproject.toml`](../configs/python/pyproject.toml) профиля содержит секции для pyink 26.5.1, isort 9.0.2 (профиль `google`), ruff 0.16.8, mypy 2.3.1 и pytest 9.1.1; pylint 4.1.2 настраивается скачанным `pylintrc`. Секции ruff, mypy и pytest проверены запуском; pyink, isort и pylint не запускались (реестр пакетов недоступен), их опции сверены с исходниками. Из набора ruff убраны `I`, `E501` и `Q000`-`Q003`: проверено запуском, что `I001`, `E501` и `ruff format` требуют переносить длинный импорт в скобках, а гайд выводит длинные импорты из-под лимита и pyink их не трогает.

**Django.** Публичных данных не найдено: в google/styleguide Django не упоминается (слово встречается только как CSS-класс в HTML/CSS-гайде). Единственный близкий документ - [AUTHORING_GUIDE](https://github.com/GoogleCloudPlatform/python-docs-samples/blob/main/AUTHORING_GUIDE.md) для примеров Google Cloud: PEP 8 и Google Python Style Guide, flake8, Black; об архитектуре Django в нём ничего нет. Профиль применяет к Django-коду общие правила G-PY и добавляет 15 правил «не Google» ([G-DJ-001 … G-DJ-015](../docs/frameworks/django.md)) из [стиля кода Django](https://docs.djangoproject.com/en/dev/internals/contributing/writing-code/coding-style/), проверок `DJ` в ruff и гайда HackSoft.

**FastAPI.** Публичных данных не найдено: FastAPI и Flask не упоминаются ни в одном файле google/styleguide. Профиль добавляет 13 правил «не Google» ([G-FAPI-001 … G-FAPI-013](../docs/frameworks/fastapi.md)) из [документации FastAPI](https://fastapi.tiangolo.com/) 0.143.0, проверок `FAST` в ruff, официального шаблона проекта и стороннего сборника практик. Официальной страницы со стилем у FastAPI нет, правила собраны из учебника.

Правила - в [other.md](../docs/languages/other.md).

**Java** - самая благополучная пара «гайд + инструмент». Гайд правили четыре раза за полтора года: в апреле 2026 запрещены module imports и compact source files и разрешены безымянные переменные `_` ([`b5c8eca`](https://github.com/google/styleguide/commit/b5c8eca)), в сентябре 2026 разрешён Markdown-Javadoc ([`8b48d07`](https://github.com/google/styleguide/commit/8b48d07)). google-java-format 1.37.0 и Error Prone 2.50.0 требуют JDK 21; форматтер не настраивается, и гайд ссылается на его вывод. Checkstyle `google_checks.xml` ведёт не Google, но он уже содержит проверки под правки 2026 года. Версию языка гайд не называет; по перечню конструкций это Java 22-25 (интерпретация). Правила - G-JAVA-001 … 010.

**Go.** Трёхчастный гайд обновлён 2026-03-18. Из инструментов он называет только `gofmt`, вывод которого обязателен и проверяется presubmit-проверкой в кодовой базе Google ([Formatting](https://google.github.io/styleguide/go/guide#formatting)); `go vet`, staticcheck и golangci-lint в тексте не упоминаются. Правила - G-GO-001 … 010.

**TypeScript и JavaScript.** Публичный TS-гайд не экспортировался с 2023-10-11 и не содержит раздела о форматировании; JS-гайд заморожен с июля 2024 года и советует переходить на TypeScript. Единственный живой инструмент - gts 7.0.0 (ESLint 9, flat config), который сам называет себя неофициальным и расходится с гайдом: `ban-ts-comment` у него лишь предупреждение, а запреты `export default`, `_`-имён, `#private` и `const enum` не проверяются вовсе ([src/index.js](https://github.com/google/gts/blob/main/src/index.js)). eslint-config-google заархивирован 2026-06-01 без объяснения и без указания замены. Правила - G-TS-001 … 010; подробности о вебе - в B.4.

**Kotlin.** Гайд живёт на developer.android.com (2026-09-22) и инструментов не называет. ktfmt, который принято считать «гугловским», создан в Meta, а летом 2026 года перешёл в организацию Kotlin: тег v0.65 от 2026-10-06 меняет пакет на `org.jetbrains.kotlinx.ktfmt` ([CHANGELOG](https://github.com/Kotlin/ktfmt/blob/main/CHANGELOG.md)). Его режим `--google-style` - внутренний стиль Google с 2 пробелами, а не публичный гайд с 4; профиль запускает ktfmt с `--kotlinlang-style`. Правила - G-KT-001 … 010.

**C#.** Гайд 2020 года без единого инструмента: ни форматтера, ни конфига Google не публикует. Машинный «Google C#» существует только как ветка пресета `Google` в clang-format, то есть в LLVM ([Format.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Format/Format.cpp)). Правила - G-CS-001 … 009.

**Языки без гайда** делятся на три случая. У Ruby есть официальный машинный конфиг без прозаического гайда - gem `google-style` 1.32.0 (G-RB-001 … 006). У Rust гайд существует внутри Google: Chromium пишет, что перейдёт на «Google Rust Style Guide», когда тот будет опубликован, а пока следует общему Rust Style Guide ([Chromium Rust style](https://chromium.googlesource.com/chromium/src/+/main/styleguide/rust/rust.md)); правила профиля G-RS-001 … 007 взяты из норм сообщества. Для PHP есть только практика google-cloud-php (PSR-2), для Scala и Elixir публичных данных не найдено; правила G-PHP-001 … 005 помечены «не Google».

**Статус инструментов, названных в брифе.** Из них официальны, поддерживаются и соответствуют гайду только google-java-format, Error Prone и pyink. За 2024-2026 годы четыре «гугловских» инструмента сменили статус или владельца: cpplint удалён из google/styleguide (2024-07-08), eslint-config-google заархивирован (2026-06-01), ktfmt перешёл в Kotlin/JetBrains (лето 2026), buildtools переехал из bazelbuild в bazel-contrib (релиз v10 в сентябре 2026, модуль `github.com/bazel-contrib/buildtools/v10`). Два последних перехода выведены из самих репозиториев: публичных объявлений о них не найдено. swift-format начинали инженеры Google, но это проект swiftlang, и «Google-конфига» у него нет.

### B.4. Фронтенд и фреймворки

Из четырёх фреймворков собственный гайд Google есть только у Angular. README google/styleguide называет его среди гайдов, живущих вне проекта ([README](https://github.com/google/styleguide/blob/gh-pages/README.md)), а 2026-09-25 из google/styleguide удалили старый гайд по AngularJS 1.x с пояснением в сообщении коммита, что гайд Angular поддерживает сам проект и Google пользуется им внутри ([коммит `570df3b`](https://github.com/google/styleguide/commit/570df3b)). Для React, Django и FastAPI гайдов Google нет.

**Angular.** Действует «редакция 2025 года»: один коммит от 2025-04-22 заменил документ из нумерованных правил «Style 01-01 … A-02» на текст из **22 правил в четырёх разделах** - именование, структура проекта, внедрение зависимостей, компоненты и директивы ([коммит `e96a0c1fc`](https://github.com/angular/angular/commit/e96a0c1fc7bc594fa714ef8f43c65f7dea6a421d)). Та же редакция действует для Angular v22.2.2 в октябре 2026 года ([angular.dev/style-guide](https://angular.dev/style-guide)). Изменился не только объём, но и статус текста. Старый гайд делил правила на Do, Consider и Avoid; новый во введении говорит, что его рекомендации не обязательны для работы Angular, ограничивается спецификой фреймворка, а за стилем TypeScript отсылает к Google TypeScript Style Guide. Поэтому в профиле почти все правила области NG имеют уровень SHOULD; MUST получили только G-NG-009, 015, 018, 022 и 028, где формулировка источника категорична или того же требует TS-гайд. Правила - [G-NG-001 … G-NG-032](../docs/frameworks/angular.md).

По содержанию редакция 2025 отказалась от трёх привычных опор старого гайда. Исчезли суффиксы типа в именах: вместо `user-profile.component.ts` и `UserProfileComponent` - `user-profile.ts` и `UserProfile` (G-NG-004). Целиком удалены разделы про NgModule (G-NG-029). Развернулись на противоположные два совета: обработчики теперь называют по действию, а не по событию (G-NG-025), а host-привязки описывают свойством `host`, а не декораторами (G-NG-028). Новые правила - `inject()` вместо параметров конструктора (G-NG-013), `protected` для членов, нужных только шаблону (G-NG-022), `readonly` для свойств, которые инициализирует Angular (G-NG-023), привязки `[class]` и `[style]` (G-NG-024). Гайд прямо не запрещает суффикс `Component`: отказ выражен примерами, удалением старых правил и умолчаниями инструментов, поэтому G-NG-004 помечено как реконструкция со средней уверенностью. Полная таблица «было - стало» - в `angular.md`.

Инструменты перестроились вместе с текстом. **Angular CLI** с 20.0.0 (2025-05-28) генерирует файлы без `.component` и `.directive`, с 21.0.0 у `ng new` есть опция `fileNameStyleGuide` со значением по умолчанию `"2025"`, а с 22.0.0 новый компонент по умолчанию работает в режиме `OnPush` ([CHANGELOG angular-cli](https://github.com/angular/angular-cli/blob/main/CHANGELOG.md), [ng-new/schema.json](https://github.com/angular/angular-cli/blob/main/packages/schematics/angular/ng-new/schema.json)). Новый workspace получает Prettier с `printWidth: 100` и `singleQuote: true`; ESLint CLI сам не добавляет ([workspace/files](https://github.com/angular/angular-cli/tree/main/packages/schematics/angular/workspace/files)). Линтер подключается отдельно - это **angular-eslint 22.5.0**, проект сообщества под MIT, а не продукт Google. Он поддерживает только flat config и только ESLint 9 и 10, требует typescript-eslint 8 и не содержит форматирующих правил ([CONFIGURING_ESLINT.md](https://github.com/angular-eslint/angular-eslint/blob/main/docs/CONFIGURING_ESLINT.md), [README](https://github.com/angular-eslint/angular-eslint/blob/main/README.md)). Правило `component-class-suffix` в нём сохранено, но помечено как не рекомендуемое командой Angular с v20 ([описание правила](https://github.com/angular-eslint/angular-eslint/blob/main/packages/eslint-plugin/docs/rules/component-class-suffix.md)). Из 32 правил области NG линтер проверяет полностью 11 и частично 6; структура каталогов, имена файлов, `protected` и имена обработчиков остаются на ручное ревью.

**TypeScript и JavaScript в вебе.** Публичный TS-гайд последний раз экспортирован 2023-10-11 и не содержит раздела о форматировании; JavaScript-гайд заморожен с июля 2024 года. Инструмент Google для TS-гайда - **gts 7.0.0** (тег 2025-12-05): в этой версии он перешёл на flat config и ESLint `^9.37.0`, но README оговаривает, что это не официальный продукт Google, а после релиза в main попал один содержательный коммит - правило `array-type` от 2026-01-16 ([package.json](https://github.com/google/gts/blob/main/package.json), [коммит `bd623c0`](https://github.com/google/gts/commit/bd623c0)). **eslint-config-google** в архиве с 2026-06-01: последний релиз 0.14.0 вышел в 2019 году, формат - eslintrc, TypeScript он не покрывает ([репозиторий](https://github.com/google/eslint-config-google)). Профиль поэтому не опирается ни на один готовый пакет: веб-конфиг собран на ESLint 10.12.0 и typescript-eslint 8.71.1, набор правил gts перенесён в него поштучно. Отдельная ловушка версий: тег `latest` пакета `typescript` указывает на 7.0.2, а typescript-eslint 8.71.1 принимает только `<6.1.0`, поэтому TypeScript нужно закреплять на 6.0.x ([реестр npm](https://registry.npmjs.org/typescript-eslint/latest)).

**HTML и CSS.** Google HTML/CSS Style Guide жив, но меняется редко: последняя содержательная правка - формат `TODO` в феврале 2025 года. Из него в профиль выписано 19 правил (G-CSS-001 … G-CSS-019, в `angular.md`). Линтера или конфига Stylelint для этого гайда у Google нет - публичных данных не найдено; [`.stylelintrc.json`](../configs/web/.stylelintrc.json) профиля собран из встроенных правил Stylelint 17.16.0 и помечен «не Google».

**React.** Публичных данных не найдено: в текстах google/styleguide слово «React» не встречается, а TSX упомянут один раз - в таблице именования TS-гайда, где функциям-компонентам предписан UpperCamelCase ([tsguide](https://google.github.io/styleguide/tsguide.html#naming-rules-by-identifier-type)). Веб-поиск официального гайда дал только сторонние документы; правила отдельных команд Google внутри их репозиториев не проверялись. Альтернатива «не Google» - официальные Rules of React на react.dev и `eslint-plugin-react-hooks` 7.1.1, который с версии 7.0.0 включает в пресет `recommended` правила React Compiler ([react.dev](https://react.dev/reference/rules), [CHANGELOG плагина](https://github.com/facebook/react/blob/main/packages/eslint-plugin-react-hooks/CHANGELOG.md)). Они оформлены как [G-REACT-001 … G-REACT-015](../docs/frameworks/react.md). Привычный `eslint-plugin-react` 7.37.5 в конфиг не вошёл: его диапазон peer заканчивается на ESLint `^9.7` ([реестр npm](https://registry.npmjs.org/eslint-plugin-react/latest)).

**Django и FastAPI.** Проверка та же и результат тот же: в `pyguide.md` и остальных файлах google/styleguide слова Django, Flask и FastAPI не встречаются. Ближайший документ Google - правила оформления Python-сэмплов Google Cloud, и к архитектуре Django или FastAPI они отношения не имеют. Вердикт для обоих фреймворков - публичных данных не найдено; альтернативы «не Google» описаны в B.2.

## C. Оформление git-репозитория

### C.1. Письменные правила

У Google три слоя письменных правил для репозитория. Первый - обязательная процедура выпуска открытого проекта, опубликованная OSPO и обновлённая 2025-06-10 ([Releasing](https://opensource.google/documentation/reference/releasing)). Она адресована сотрудникам Google и защищает права компании, поэтому слово «must» в ней встречается там, где речь о юридическом минимуме: файл `LICENSE` ([G-REPO-001](../docs/git/repository.md)), Apache-2.0 по умолчанию (G-REPO-002), заголовок с копирайтом и лицензией в каждом исходном файле (G-REPO-010, 011, 013), раздел о CLA в `CONTRIBUTING` (G-REPO-003, 017), каталог `third_party/` для чужого кода (G-REPO-014, 015) и дисклеймер для неофициальных проектов (G-REPO-018). README там назван минимумом, который «следует» дать, а кодекс поведения и политика безопасности прямо помечены как необязательные (G-REPO-004, 005). Та же документация требует закреплять сторонние действия GitHub Actions на конкретный коммит («a fixed version of the action MUST be used», [github/services](https://opensource.google/documentation/reference/github/services); G-REPO-024) и защищать основные ветки. Второй слой - документация: docguide из google/styleguide задаёт разметку Markdown и содержание README (G-DOC-001 … 010), Google developer documentation style guide - язык документации (G-DOC-011). Оба написаны как рекомендации; жёсткое требование в них одно - файл должен называться `README.md`. Третий слой - процесс: [eng-practices](https://google.github.io/eng-practices/) описывает ревью и описания изменений, README google/styleguide с 2025-01-17 советует статью cbea.ms для сообщений коммитов, политика OSPO о несовместимых изменениях и документация release-please - релизы.

Шаблон [google/new-project](https://github.com/google/new-project) минимален. В нём шесть файлов: `README.md`, `LICENSE`, `docs/contributing.md`, `docs/code-of-conduct.md`, шаблон PR и шаблон сообщения об ошибке. В нём нет `SECURITY.md`, `CODEOWNERS`, `.gitignore`, changelog и ни одного CI-файла. Политику безопасности и общие правила поведения Google задаёт на уровне организации, в репозитории [google/.github](https://github.com/google/.github), откуда GitHub подставляет файлы во все проекты.

**Коммиты.** Общий слой один - раздел eng-practices об описаниях изменений: короткая первая строка в повелительном наклонении, пустая строка, тело «что и почему»; чисел длины, правил о регистре и точке там нет ([G-GIT-001 … 003, 006, 008, 012, 016](../docs/git/commits.md)). Форму задаёт сторонняя статья: с 2025-01-17 README стайлгайдов советует [«How to Write a Git Commit Message»](https://cbea.ms/git-commit/) с её ориентиром в 50 и пределом в 72 символа (G-GIT-004, 005, 007); сообщение коммита [`a47f7e5`](https://github.com/google/styleguide/commit/a47f7e5) объясняет это тем, что многие проекты Google уже ссылаются на эту статью. Go, Chromium, AOSP и Angular держат собственные форматы - префикс пакета у Go, трейлер `Bug:` у Chromium, `Signed-off-by` и предел 50 символов у AOSP, восемь типов у Angular; Conventional Commits обязателен только в Angular и в репозиториях с release-please (G-GIT-013, 014).

**Ветки, ревью, релизы.** Про ветки письменных git-правил почти нет: trunk-based development описан в SWE и в рекомендациях DORA, а для GitHub закреплены только требование ревью в шаблоне new-project и защита основных веток в документе OSPO о GitHub Actions ([G-BR-001 … 013](../docs/git/branches.md)). Ревью описывает eng-practices ([G-CR-001 … 018](../docs/git/code-review.md)): одобрять изменение, которое однозначно улучшает здоровье кода, даже если оно неидеально; отвечать в течение одного рабочего дня; помечать необязательные замечания «Nit:»; гайд по стилю - «absolute authority», а крупное переформатирование отправляется отдельным изменением; ориентир размера - около 100 строк, 1000 - обычно слишком много ([Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html#what-is-small)). По релизам есть политика OSPO о несовместимых изменениях, которая действует только для присоединившихся к ней проектов и не обновлялась с 2023-01-18 ([G-REL-001, 006, 007](../docs/git/releases.md)), и документация release-please (G-REL-009 … 011).

### C.2. Выборка и метод

Практика измерена 2026-10-09 по 24 репозиториям из десяти организаций и шаблону `google/new-project` как эталону (список - в разделе «Метод»). Проанализировано 7 006 сообщений коммитов (7 041 с шаблоном), по 300 последних на репозиторий; для заголовков лицензии - 240 файлов; ветки и теги - через `git ls-remote`. Суффикс `(#N)`, то есть след слитого PR, несут 2 976 коммитов; 450 коммитов содержат строку, закрывающую задачу или PR. Число ревьюеров, время до слияния и настройки защиты веток не измерялись: они доступны только через API; настройки видны лишь там, где лежат в репозитории как код (3 из 24). История Gerrit-проектов взята с зеркал: 40 и 300 коммитов golang/go (две выборки), 60 - chromium/src, 60 - AOSP frameworks/base; отдельные коммиты сверены на самих хостах.

**Главный результат: практика делится не по языкам, а по модели разработки.** 12 репозиториев из 24 - односторонний экспорт из внутреннего монорепозитория через Copybara (трейлер `PiperOrigin-RevId` в большинстве коммитов). В таких репозиториях PR не сливают кнопкой GitHub - внешние изменения импортируются внутрь и возвращаются коммитом экспорта, а CI часто живёт внутри компании. Остальные 12 ведутся прямо на GitHub; только по ним можно судить о командных настройках.

Исключение - AOSP: в документированный предел 50 символов укладываются 33 заголовка из 60. Три репозитория с настройками как кодом совпадают: merge-коммиты запрещены, одно обязательное одобрение, одобрение владельцев кода, обязательные проверки.

### C.5. Где практика расходится с письменным правилом

Устойчиво соблюдается только юридический минимум: файлы лицензии и CONTRIBUTING есть везде, CLA требуют все, заголовки стоят в четырёх репозиториях из пяти. Дальше начинаются расхождения. Дисклеймер, который OSPO называет обязательным для неофициальных проектов, найден в 8 из 24 README, причём точная формулировка «not an officially supported Google product» - в одном (pyink), а остальные семь пишут «not an official Google product». Шаблон предписывает правообладателя `Google LLC`, но так делают 5 из 24 - все из googleapis и GoogleCloudPlatform; 11 используют «The [Project] Authors» с файлом AUTHORS, как разрешает [отдельная страница OSPO](https://opensource.google/documentation/reference/releasing/authors). Keras распространяется под Apache-2.0 вовсе без заголовков в файлах. OSPO рекомендует addlicense, но ни один из 25 репозиториев его не вызывает: googleapis пользовались ботом `header-checker-lint`, который объявлен устаревшим, а optax, jax и tensorflow держат собственные скрипты. Требование OSPO закреплять сторонние действия GitHub Actions на коммит выполняет половина выборки, а flatbuffers, microservices-demo и re2 не закрепляют ни одного. Рекомендация избегать пары master/slave (G-REPO-019) не распространилась задним числом на имена веток: 9 из 24 репозиториев остаются на `master`.

В коммитах расхождение того же рода. Примеры eng-practices ставят точку в конце первой строки, и в 12 репозиториях из 24 она есть не менее чем в 30 % коммитов, тогда как cbea.ms, Go и Angular точку запрещают. Ориентир cbea.ms в 50 символов выдерживают 8 репозиториев из 24; медиана - 56, 90-й перцентиль - 84. commitlint не настроен ни в одном репозитории - сообщения проверяют только Angular (собственным `ng-dev`) и проекты на Gerrit (хуки). Заметно и то, чего экспорт не переносит: в экспортируемых репозиториях merge-коммитов 10,3 %, заголовки с заглавной буквы - 86 %, а в репозиториях, живущих на GitHub, 79 % коммитов - squash с суффиксом `(#N)`.

Расхождение есть и в обратную сторону: практика богаче шаблона. `CODEOWNERS` (9 из 24), `.gitignore` (23), YAML-формы issue (7), Dependabot или Renovate (15) в письменных правилах не упомянуты вовсе; правила G-REPO-006, 020 и 022 поэтому помечены как реконструкция, как и G-BR и G-REL, построенные на долях выборки (14 правил областей GIT, BR, CR и REL - реконструкции).

**Чего нет.** Требований OSPO к `CHANGELOG`, `.gitignore`, `.editorconfig`, `CODEOWNERS` и шаблонам issue - публичных данных не найдено. Формата файлов `METADATA` и `README.google` в `third_party/` - публичных данных не найдено: [открытая страница](https://opensource.google/documentation/reference/thirdparty/new) содержит только обзор из пяти шагов. Официального `.pre-commit-config.yaml`, линтера Markdown и CI-шаблона - публичных данных не найдено. Инструмента проверки лицензий зависимостей - публичных данных не найдено. Публичных данных не найдено о языке сообщений (есть только практика: 24 из 24 на английском, G-GIT-011), об именах рабочих веток, о подписи коммитов и тегов, о формате changelog вне release-please, о чек-листе ревьюера, о применении readability вне монорепозитория. Официальной рекомендации по `CODEOWNERS` нет: документы OSPO и new-project о нём не упоминают. Правил, шаблонов и CI для GitLab - публичных данных не найдено: [страница OSPO о хостинге](https://opensource.google/documentation/reference/releasing/hosting) рекомендует GitHub, упоминает Gerrit и не упоминает GitLab; release-please работает только с GitHub. Шаблоны для GitLab в профиле - перенос с пометкой «не Google»; платформенные различия сведены в таблицу в [repository.md](../docs/git/repository.md).

Ядро публичных сведений о внутренней инженерной системе Google - три слоя: книга «Software Engineering at Google» (SWE; первое издание 2020-02-28, бесплатный PDF с 2021-04-22, HTML на abseil.io с 2022-05-04; лицензия CC BY-NC-ND 4.0, поэтому здесь только пересказ), статьи в CACM и на ICSE 2013-2018 годов и экспортированные репозитории (styleguide, eng-practices, Abseil, Bazel, Copybara, Kythe). Почти всё описывает состояние до 2020 года: цифры SWE относятся к ≈2019 году, цифры CACM - к январю 2015 года. Официальных количественных данных о монорепозитории после 2020 года не найдено. Даты ввода Piper, CitC, Critique, TAP, Rosie и Tricorder во внутреннюю эксплуатацию - публичных данных не найдено; известны только даты статей.

### D.1. Piper и CitC

Почти весь код Google лежит в одном репозитории под собственной централизованной VCS **Piper**, которая работает как распределённый сервис в продакшен-среде компании; Chromium и Android живут отдельно ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#version_control_at_google), 2020) и используют git (выдержка CACM 2016 у [mjtsai](https://mjtsai.com/blog/2016/06/30/why-google-stores-billions-of-lines-of-code-in-a-single-repository); уверенность средняя). До Piper более десяти лет использовался один сервер Perforce; Piper хранит данные в Bigtable, затем Spanner, в десяти дата-центрах с консенсусом Paxos - это пересказ статьи CACM 2016 в сторонних источниках ([Wikipedia: Piper](https://en.wikipedia.org/wiki/Piper_(source_control_system)); уверенность средняя). Причина создания собственной системы по CACM: подходящей коммерческой или открытой системы не нашлось ([выдержка у mjtsai](https://mjtsai.com/blog/2016/06/30/why-google-stores-billions-of-lines-of-code-in-a-single-repository); уверенность средняя). Год ввода Piper и точная дата отказа от Perforce - публичных данных не найдено.

Масштаб, с датой при каждой цифре. На январь 2015 года: 86 ТБ, около миллиарда файлов, из них около 9 млн исходных, около 2 млрд строк кода, около 35 млн коммитов за 18 лет истории, около 40 тыс. коммитов в рабочий день, из которых примерно 16 тыс. делают люди и 24 тыс. - автоматика ([Henderson, arXiv 1702.01715](https://arxiv.org/pdf/1702.01715), 2017; [CACM 2016](https://research.google/pubs/why-google-stores-billions-of-lines-of-code-in-a-single-repository/) в пересказах). К ≈2019 году: более 80 ТБ, 60-70 тыс. коммитов в рабочий день, около 50 тыс. инженеров и около 1000 команд в монорепозитории ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#version_control_at_google)); более 2 млрд строк и около 25 млн изменяемых строк в неделю, примерно половина - автоматикой ([SWE гл. 11](https://abseil.io/resources/swe-book/html/ch11.html#testing_at_google_scale)); по abseil.io - более 250 млн строк C++ (дата цифры на странице не указана; [Philosophy](https://abseil.io/about/philosophy)). Расхождения источников: разные главы SWE называют 30 тыс. и 50 тыс. инженеров; сторонняя рассылка приводит для 2016 года 45 тыс. коммитов в день против 40 тыс. у Хендерсона - в отчёте используются цифры Хендерсона и CACM с датой «январь 2015». Создать клиент, добавить файл и закоммитить занимает около 15 секунд; номера ревизий монотонно растут, и на этом построено много внутренних скриптов ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#distributed_vcs)).

**CitC (Clients in the Cloud)** - облачные рабочие области поверх Piper: FUSE-вид на весь репозиторий, локально хранятся только изменённые файлы, каждая запись сохраняется как снимок; большинство разработчиков работает именно так, а в средней рабочей области меньше десяти изменённых файлов (выдержки CACM 2016 у [mjtsai](https://mjtsai.com/blog/2016/06/30/why-google-stores-billions-of-lines-of-code-in-a-single-repository) и в [Wikipedia](https://en.wikipedia.org/wiki/Piper_(source_control_system)); уверенность средняя). Доля пользователей Piper на CitC - более 80 % в 2015 году (сторонний пересказ, уверенность низкая). Примечательно, что термин CitC в тексте SWE не встречается (проверено поиском по главам). Помимо CitC существуют клиенты с привычным интерфейсом: Fig - клиент на основе Mercurial, которому Google готовит замену в виде Jujutsu - об этом сообщает только [сторонняя расшифровка доклада](https://nest.pijul.com/fetsorn/pijul-spec:main/4NBQFWD6E7ZJM.OH2Q2) инженера Google (дата доклада не указана, уверенность низкая); README проекта Jujutsu называет систему Google «Piper/CitC» ([jj README](https://github.com/jj-vcs/jj/blob/main/README.md)). Попытки приблизить рабочий процесс к привычному для новичков авторы SWE называют периодическими ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#distributed_vcs)). Доли пользователей разных клиентов - публичных данных не найдено.

Почему не git. Авторы SWE объясняют: главный репозиторий не перешёл на git из-за размера, числа пользователей и накопленных зависимостей от текущего интерфейса (закон Хайрама); при их масштабе разработчик работает с малой долей файлов, поэтому передача всей истории и кода, которую предполагает DVCS, - почти целиком потери; у git известны проблемы с производительностью после нескольких миллионов коммитов и с большими бинарными файлами ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#distributed_vcs), [#monorepos](https://abseil.io/resources/swe-book/html/ch16.html#monorepos)). При этом те же авторы не считают монорепозиторий единственным путём и допускают, что вложение в «виртуальный монорепозиторий» поверх обычных инструментов могло быть лучше, чем Piper ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#future_of_version_control)). Опрос инженеров (ICSE-SEIP 2018) называет главным плюсом монорепозитория видимость кода и централизованное управление зависимостями, плюсами множества репозиториев - свободу выбора инструментов, контроль доступа и стабильность; исход сильно зависит от инструментов ([research.google/pubs/pub47040](https://research.google/pubs/pub47040); прочитана только аннотация). Почти весь код виден каждому инженеру ([SWE гл. 22](https://abseil.io/resources/swe-book/html/ch22.html#policies_and_culture)); закрытых файлов меньше 1 % по состоянию на 2016 год (пересказ CACM, уверенность средняя). Поиск и чтение кода делает отдельный веб-инструмент Code Search: индекс поиска обновляется с каждым изменением, а индекс перекрёстных ссылок (Kythe) пересобирается раз в сутки - отдельный инструмент нужен, потому что полная копия кодовой базы не помещается на одну машину ([SWE гл. 17](https://abseil.io/resources/swe-book/html/ch17.html#scale)); публичная версия для открытых проектов Google запущена 2020-04-01 ([блог](https://opensource.googleblog.com/2020/04/code-search-for-google-open-source.html)).

**Владение.** Файлы `OWNERS` лежат на каждом уровне дерева и перечисляют тех, кто может одобрять коммиты в поддереве; права складываются вверх по дереву, проверку выполняет сама VCS при коммите ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#version_control_at_google), [гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#how_code_review_works_at_google)). У каждого поддерева должно быть минимум два владельца; менять код может кто угодно, но с одобрения владельца ([Henderson](https://arxiv.org/pdf/1702.01715), 2017). Корневой `OWNERS` служит списком глобальных одобряющих для крупномасштабных изменений ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#how_code_review_works_at_google)). Сторонний код кладут в `third_party`; чек-лист импорта: собирается внутренней системой сборки, нет другой версии, минимум два владельца в `OWNERS`; авторы признают слабость этой политики ([SWE гл. 21](https://abseil.io/resources/swe-book/html/ch21.html#how_google_handles_importing_dependende)).

### D.2. Critique и readability

**Процесс ревью.** Ревью обязательно почти для любого изменения; исключения - часть правок документации и конфигураций ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#code_review_benefits)). Изменение должно набрать три вида одобрения: LGTM от коллеги - проверка корректности и понятности; одобрение владельца из `OWNERS`; одобрение человека с readability по языку. Автор может сам закрывать второе и третье, если он владелец и у него есть readability, но LGTM всегда даёт другой человек ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#how_code_review_works_at_google)). В Critique изменение можно коммитить, когда есть хотя бы один LGTM, достаточные одобрения и нет неразрешённых комментариев; оценки только положительные - от «Needs More Work» и «LGTM++» отказались, негатив выражается конкретным неразрешённым комментарием ([SWE гл. 19](https://abseil.io/resources/swe-book/html/ch19.html#stage_five_change_approvals_left_parent)). Принципы Critique - простота, доверие, общие средства общения, интеграция с другими инструментами ([SWE гл. 19](https://abseil.io/resources/swe-book/html/ch19.html#code_review_tooling_principles)); из Critique вызывается веб-редактор Cider, а результаты статического анализа показываются прямо в ревью. Главной пользой ревью названа не корректность, а понятность и сопровождаемость кода ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#code_correctness)); исследование подтверждает, что основной мотив - обучение и поддержание норм ([Modern Code Review](https://sback.it/publications/icse2018seip.pdf), 2018).

**Статистика** по статье ICSE-SEIP 2018 (около 9 млн изменений, январь 2014 - июль 2016, более 25 тыс. авторов и ревьюеров): медианный размер изменения - 24 строки; более 35 % меняют один файл, около 90 % - меньше десяти файлов, более 10 % - одну строку; медианное число ревьюеров - 1, больше одного - менее чем у 25 % изменений; первый отклик - медиана меньше часа для малых изменений и около пяти часов для очень больших; всё ревью - медиана меньше четырёх часов; около 70 % изменений закоммичены в течение 24 часов после отправки; автор делает около трёх изменений в неделю (медиана), ревьюер смотрит около четырёх, на ревью уходит в среднем 3,2 часа в неделю; 97 % разработчиков довольны Critique по внутренним опросам; новички получают более чем вдвое больше комментариев на изменение ([PDF](https://sback.it/publications/icse2018seip.pdf)). Нормы: «малое» изменение - примерно до 200 строк, инструмента, автоматически отклоняющего большие изменения, нет - решает ревьюер ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#write_small_changes)); большинство изменений меньше 100 строк ([SWE гл. 19, сноска](https://abseil.io/resources/swe-book/html/ch19.html#conclusion-id00023)); отклик ожидается в течение 24 рабочих часов ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#be_polite_and_professional)), а публичный гайд называет один рабочий день максимумом ([Speed of Code Reviews](https://google.github.io/eng-practices/review/reviewer/speed.html#fast)). Старые инструменты помечали изменения больше 300 строк насмешливыми ярлыками, новые ставят размер S/M/L/XL ([Henderson](https://arxiv.org/pdf/1702.01715)). Интерпретация: норма «один ревьюер, малое изменение, ответ за день» - оптимизация пропускной способности, а не качества отдельного ревью; авторы прямо пишут, что первый LGTM важнее последующих ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#keep_reviewers_to_a_minimum)).

**История инструментов.** Mondrian - внутренний инструмент ревью, привязанный к Perforce и Bigtable; публичный доклад Гвидо ван Россума о нём прошёл 2006-11-30 ([Google Developers Blog, 2006](https://developers.googleblog.com/2006/11/announcing-open-source-developers.html)). Rietveld - открытый инструмент «по мотивам» Mondrian, 2008-05-08 ([блог, 2008](https://developers.googleblog.com/en/guido-van-rossum-releases-mondrian-clone-rietveld/)). Gerrit создан для AOSP как набор патчей к Rietveld, затем форк; Google применяет его для своих git-проектов ([gerritcodereview.com](https://www.gerritcodereview.com/about.html); [SWE гл. 9, сноска](https://abseil.io/resources/swe-book/html/ch09.html#code_review-id00002)). Год запуска Critique и вывода Mondrian - публичных данных не найдено; статья 2018 года Mondrian не называет.

**Readability** - в Google это не свойство кода, а статус человека и вид одобрения: общекомпанейский стандартизованный процесс наставничества по языку, который охватывает идиомы, структуру кода, дизайн API, общие библиотеки, документацию и тесты ([SWE гл. 3](https://abseil.io/resources/swe-book/html/ch03.html#readability_standardized_mentorship_thr)). Происхождение: Крейг Сильверстайн, сотрудник № 3, лично построчно разбирал первый крупный коммит каждого новичка (там же). Правило: каждое изменение требует readability-одобрения; сертифицированный автор даёт его сам себе; по Хендерсону оно требуется для изменений, добавляющих нетривиальный новый код на языке ([SWE гл. 3](https://abseil.io/resources/swe-book/html/ch03.html#what_is_the_readability_processquestion); [Henderson](https://arxiv.org/pdf/1702.01715)). Сертификация: автор отправляет изменения централизованной группе ревьюеров, замечаний становится меньше, после чего readability присваивают; в процессе в любой момент участвуют около 20 % инженеров, ревьюеров - около 1-2 %, все волонтёры (≈2019); сертификация отдельная по каждому языку ([SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#code_consistency)). Исключения: код с коротким сроком жизни - каталог `experimental/`, программа Area 120 ([SWE гл. 3, сноска](https://abseil.io/resources/swe-book/html/ch03.html#why_have_this_processquestion_mark)). Издержки и критика описаны самими авторами: трение для команд без сертифицированных участников, лишние раунды ревью, линейное масштабирование; часть инженеров считает процесс бюрократией и называла его «hazing ritual» ([SWE гл. 3](https://abseil.io/resources/swe-book/html/ch03.html#why_have_this_processquestion_mark), [гл. 7](https://abseil.io/resources/swe-book/html/ch07.html#triage_is_it_even_worth_measuringquesti)). Внутреннее исследование показало, что изменения авторов с readability проходят ревью и коммитятся статистически значимо быстрее с поправкой на стаж и число раундов, а самооценка качества кода выше; процентов и времени в книге нет; команда readability заранее обязалась закрыть процесс по языку, если польза не подтвердится ([SWE гл. 7](https://abseil.io/resources/swe-book/html/ch07.html#taking_action_and_tracking_results)). Readability действует только в монорепозитории, потому что это понятие единообразия внутри одного репозитория ([SWE гл. 3, сноска 20](https://abseil.io/resources/swe-book/html/ch03.html#why_have_this_processquestion_mark)); публичный Go-гайд называет аудиторией документа «Style Decisions» наставников readability ([Go Style](https://google.github.io/styleguide/go/)). Число языков с readability, длительность получения, доля отказов - публичных данных не найдено. Интерпретация: readability - человеческий механизм для той доли правил, которую нельзя автоматизировать; авторы ожидают, что по мере роста статического анализа ревьюеры сосредоточатся на понятности кода.

### D.3. Как создаются и применяются правила стиля

Правила Google - обязательные «законы», а не советы: отступать от них можно только по одобренному исключению, а рекомендации («guidance») - отдельная категория; «стиль» при этом шире форматирования - это полный набор соглашений о коде ([SWE гл. 8](https://abseil.io/resources/swe-book/html/ch08.html#style_guides_and_rules), 2020). Пять принципов: правила должны оправдывать свой вес (очевидное не записывают - нет правила про `goto`); оптимизировать для читателя, а не для пишущего; быть единообразным - в иерархии файл → команда → проект → кодовая база, причём единообразие нужно и инструментам; избегать подверженных ошибкам и неожиданных конструкций; уступать практичности ([Guiding Principles](https://abseil.io/resources/swe-book/html/ch08.html#guiding_principles)). Три категории правил: избежать опасностей; закрепить лучшие практики; обеспечить единообразие там, где технической разницы нет, - «решение ради решения»; новые возможности языка сначала ограничивают, затем расширяют по мере накопления запросов на исключения ([The Style Guide](https://abseil.io/resources/swe-book/html/ch08.html#the_style_guide)). Те же цели публично заявляет раздел «Goals» C++-гайда (с 2015-09-11): оптимизировать для читателя, согласованность с существующим кодом и, когда уместно, с сообществом C++, избегать опасных и трудных для среднего программиста конструкций, помнить о масштабе - «100+ million lines» и тысячи инженеров ([cppguide#Goals](https://google.github.io/styleguide/cppguide.html#Goals)); Go-гайд ранжирует принципы как Clarity, Simplicity, Concision, Maintainability, Consistency ([go/guide](https://google.github.io/styleguide/go/guide#style-principles)).

**Кто решает.** У каждого языка свой гайд и своя группа владельцев - арбитров стиля, обычно давних экспертов из команды библиотек языка; решения принимают консенсусом, без голосования; в C++ группа из четырёх человек (≈2019) ([The Style Arbiters](https://abseil.io/resources/swe-book/html/ch08.html#the_style_arbiters)). Предложение изменить правило должно показать существующую проблему на реальном коде Google, а не гипотетическую; любой инженер может начать обсуждение в рассылке по стилю данного языка, сообщество отсеивает, арбитры утверждают; у каждого правила фиксируют «за» и «против», чтобы понимать, когда его пересматривать ([The Process](https://abseil.io/resources/swe-book/html/ch08.html#the_process), [Changing the Rules](https://abseil.io/resources/swe-book/html/ch08.html#changing_the_rules)). Исключения выдают арбитры и неохотно; довод «так короче» или «так единообразнее в проекте» не принимается ([Exceptions](https://abseil.io/resources/swe-book/html/ch08.html#exceptions)). Единого «комитета по стилю» в источниках нет; состав арбитров, тексты рассылок и число выданных исключений - публичных данных не найдено. Два задокументированных пересмотра показывают, как правила уступают внешнему миру: Python-гайд сначала требовал отступ в 2 пробела и `CamelCase` для методов ради согласованности с C++, позже разрешён `snake_case`, а для Starlark выбран отступ 4 - мотив назван прямо: трудности при открытии кода и настороженность сообщества к «странному» стилю ([Setting the Standard](https://abseil.io/resources/swe-book/html/ch08.html#setting_the_standard)); от обещания почти не менять C++-правила ради единообразия старого кода отказались сознательно, потому что кодовая база больше никогда не будет полностью единообразной ([At Scale](https://abseil.io/resources/swe-book/html/ch08.html#advantages_of_consistency)).

**Применение.** Автоматизация предпочтительна: не забывается, не зависит от трактовки, масштабируется без роста затрат; часть правил оставлена людям намеренно - суждение, социальные нормы, размер изменения ([Applying the Rules](https://abseil.io/resources/swe-book/html/ch08.html#applying_the_rules)). Форматтеры обязательны через presubmit: если запуск форматтера даёт diff, коммит отклоняется; названы clang-format для C++, внутренняя обёртка над yapf для Python, gofmt, dartfmt и buildifier (≈2019; [Code Formatters](https://abseil.io/resources/swe-book/html/ch08.html#code_formatters)); google-java-format в этой главе не назван. Анализаторы - clang-tidy для C++ и Error Prone для Java; по неформальной оценке середины 2018 года около 90 % правил C++-гайда можно проверять автоматически ([Error Checkers](https://abseil.io/resources/swe-book/html/ch08.html#error_checkers)). С появлением clang-format число формальных правил перестало быть нагрузкой на память инженера ([SWE гл. 8, сноска 2](https://abseil.io/resources/swe-book/html/ch08.html#rules_must_pull_their_weight)). Исток культуры обязательного форматирования - gofmt: Go открыт 2009-11-10 вместе с форматтером, потому что ввести единый формат после релиза было бы почти невозможно; мотивы - убрать споры о форматировании из ревью и дать основу для машинного редактирования кода (gofix перед Go 1.0, 2012) ([go.dev/blog/gofmt](https://go.dev/blog/gofmt), 2013-01-23). В 2012 году buildifier переформатировал около 200 тыс. BUILD-файлов; согласование с владельцами заняло у одного инженера шесть недель (там же, SWE гл. 8). Актуальна ли оценка «90 %» и состав обязательных форматтеров после 2020 года - публичных данных не найдено; косвенно: публичный Python-гайд с февраля 2023 года называет Black и Pyink вместо yapf.

### D.4. Presubmit-проверки, Tricorder и TAP

Правила доводятся до кода четырьмя механизмами: компилятор, Tricorder в ревью, presubmit и массовые правки (D.7). **Компилятор:** предупреждений нет - проверка либо ошибка, либо не показывается в выводе компилятора, и тогда её место в ревью; действует для Java и C++; критерии проверки-ошибки - исправима механически, без эффективных ложных срабатываний, только про корректность, не про стиль; перед включением проверки всю кодовую базу чистят автоматически ([SWE гл. 20](https://abseil.io/resources/swe-book/html/ch20.html#compiler_integration)). На январь 2018 года в Error Prone 733 проверки от 162 авторов ([CACM 2018](https://cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google/)).

**Tricorder** показывает результаты статического анализа прямо в Critique: более 50 тыс. изменений в день, более 100 анализаторов, большинство написано вне команды Tricorder, более 30 языков (≈2019; [SWE гл. 20](https://abseil.io/resources/swe-book/html/ch20.html#tricorder_googleapostrophes_static_anal)). Критерии новой проверки: понятна; применима и легко исправляется; менее 10 % «эффективных ложных срабатываний» - случаев, когда разработчик не предпринял действия; может заметно влиять на качество; общий уровень таких срабатываний - чуть ниже 5 % ([Focus on Developer Happiness](https://abseil.io/resources/swe-book/html/ch20.html#focus_on_developer_happiness)). Обратная связь - кнопки «Not useful» и «Please fix»: около 3000 автоисправлений в день, «Not useful» нажимают около 250 раз в день; стилевые замечания должны исправляться автоматически, указывать на форматирование - плохое использование времени ревьюера ([Suggested Fixes](https://abseil.io/resources/swe-book/html/ch20.html#suggested_fixes)). На январь 2018 года - 146 анализаторов (125 от внешних для команды авторов); анализатор отключают, если «Not useful» превышает 10 % ([CACM 2018](https://cacm.acm.org/research/lessons-from-building-static-analysis-tools-at-google/)). Настройка только на уровне проекта, не пользователя: пользовательские настройки скрывали баги анализаторов ([Per-Project Customization](https://abseil.io/resources/swe-book/html/ch20.html#per-project_customization)). Ранние попытки - панель FindBugs (2006), заведение багов BugBot (2009), комментарии в ревью (закрыто в 2011) - не прижились вне основного рабочего процесса (CACM 2018). Открытая платформа статического анализа с подключаемыми анализаторами, Shipshape, - ближайший публичный родственник Tricorder (её README Tricorder не называет, но авторы коммитов пересекаются с авторами статьи о Tricorder); помечена неподдерживаемой с 2019-02 и в архиве с 2021-10-12 ([репозиторий](https://github.com/google/shipshape)).

**Presubmit** - проверка, блокирующая коммит; встроенные примеры: текст «DO NOT SUBMIT» в описании, наличие тестов, форматирование; команды добавляют свои; запускается при отправке на ревью и ещё раз при коммите ([Presubmits](https://abseil.io/resources/swe-book/html/ch20.html#presubmits), [SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#automate_where_possible)). В presubmit - только быстрые и надёжные тесты, обычно тесты проекта, где сделано изменение ([SWE гл. 23](https://abseil.io/resources/swe-book/html/ch23.html#presubmit_versus_postsubmit)). Полный прогон до коммита слишком дорог; кроме того, возможны «mid-air collisions» двух одновременно проверенных изменений - на масштабе Google почти ежедневно; малые репозитории могут избежать их, сериализуя коммиты ([SWE гл. 23](https://abseil.io/resources/swe-book/html/ch23.html#why_presubmit_isnapostrophet_enough)). Командные presubmit мешают массовым изменениям, поэтому часть пропускается при `CLEANUP=` в описании (SWE гл. 20).

**TAP (Test Automation Platform)** - глобальная непрерывная сборка всего кода: более 50 тыс. уникальных изменений и более 4 млрд тестовых случаев в день (≈2019; [SWE гл. 23](https://abseil.io/resources/swe-book/html/ch23.html#ci_at_google)). Изменение, прошедшее presubmit, с вероятностью 95 %+ проходит остальные тесты; среднее ожидание перед коммитом - около 11 минут. После коммита TAP асинхронно запускает все затронутые тесты, группируя изменения в пачки; набор тестов определяется по глобальному графу зависимостей (Blaze и Forge); виновника поломки ищут разбиением пачки и бинарным поиском; поломку чинит дежурный Build Cop, предпочтительное действие - откат, и TAP умеет откатывать автоматически при высокой уверенности; изменения с меньшим числом тестов проходят быстрее, что подталкивает к малым изменениям (там же). Результаты сборок и тестов хранит внутренний сервис Sponge - публично он виден только по имени класса в справочнике Trade Federation ([source.android.com](https://source.android.com/reference/tradefed/com/google/android/tradefed/result/teststorage/SpongeUtils); уверенность низкая). Актуальные (после 2020 года) цифры Tricorder и TAP - публичных данных не найдено.

### D.5. Blaze/Bazel и правило одной версии

**Blaze** - внутренняя система сборки; в 2015 году Google открыл её реализацию под именем **Bazel** (бета 2015-09-01; [SWE гл. 18](https://abseil.io/resources/swe-book/html/ch18.html#build_systems_and_build_philosophy), [блог Bazel](https://blog.bazel.build/2015/09/01/beta-release.html)). Bazel делит с внутренним инструментом большую часть кода; интеграции с внутренними технологиями не открыты ([Bazel FAQ](https://bazel.build/about/faq)). Шаги сборки герметичны - зависят только от объявленных входов - и распределяются на сотни и тысячи машин ([Henderson](https://arxiv.org/pdf/1702.01715), 2017); Bazel изолирует действия в песочнице файловой системы, удалённый кэш Google - ObjFS, удалённое исполнение - Forge ([SWE гл. 18](https://abseil.io/resources/swe-book/html/ch18.html#distributed_builds_at_google)). Определение герметичности: сборка изолирована от хоста и даёт одинаковый результат при одинаковых исходниках и конфигурации; инструменты трактуются как исходный код ([bazel.build/basics/hermeticity](https://bazel.build/basics/hermeticity)). Правило 1:1:1 и мелкие цели сборки с минимальной видимостью модулей ([SWE гл. 18](https://abseil.io/resources/swe-book/html/ch18.html#using_fine-grained_modules_and_the_oneo)). Герметичная сборка - то, что позволяет TAP считать затронутые тесты по графу зависимостей.

**One Version Rule.** Формулировка книги: у разработчика никогда не должно быть выбора, от какой версии компонента зависеть ([SWE гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#the_quotation_markone_versionquotation)). Для сторонних пакетов - одна версия в репозитории; для внутренних - никаких форков без переименования ([#one_version](https://abseil.io/resources/swe-book/html/ch16.html#one_version)). Правило не абсолютно: при обновлении временно сосуществуют две версии, мелкие нарушения есть (сноски 9-11 той же главы). Для сторонних зависимостей правило строгое из-за ромбовидных зависимостей ([SWE гл. 18](https://abseil.io/resources/swe-book/html/ch18.html#the_one-version_rule)). В монорепозитории соблюдать его тривиально, но авторы не считают монорепозиторий единственным путём: важен принцип, а не способ хранения ([#monorepos](https://abseil.io/resources/swe-book/html/ch16.html#monorepos)), и рекомендуют принцип и без монорепозитория ([TL;DR гл. 16](https://abseil.io/resources/swe-book/html/ch16.html#tlsemicolondrs-id00122)). С ним связана модель **Live at Head**: всегда зависеть от текущей версии и не менять API так, чтобы зависимым было трудно адаптироваться; безопасность изменения проверяют CI зависимых проектов ([SWE гл. 21](https://abseil.io/resources/swe-book/html/ch21.html#live_at_head)). Abseil публично просит пользователей жить «at head» и обещает инструмент рефакторинга при ломающих изменениях ([Philosophy](https://abseil.io/about/philosophy)). Интерпретация: та же логика «открытый код должен быть пригоден для внутренней кодовой базы» стоит за советом C++-гайда не использовать исключения в открытых проектах.

**Тесты.** Размеры тестов: small - один процесс, medium - одна машина с сетью только до localhost, large - без ограничений; деление по размеру, а не по типу «unit/integration», потому что главные свойства набора тестов - скорость и детерминизм; ограничения может проверять инфраструктура ([SWE гл. 11](https://abseil.io/resources/swe-book/html/ch11.html#test_size)). В Bazel размеры закреплены таймаутами: small 60 с, medium 300 с, large 900 с, enormous 3600 с ([Test encyclopedia](https://bazel.build/reference/test-encyclopedia)). Правило Бейонсе: всё, что не должно ломаться, должно быть покрыто автоматическим тестом; если инфраструктурное изменение прошло все тесты и сломало продукт, чинит команда продукта ([SWE гл. 11](https://abseil.io/resources/swe-book/html/ch11.html#the_beyonceacutesemicolon_rule)). История: «революция тестирования» 2005-2006 годов, рассылка Testing on the Toilet с апреля 2006 года, программа Test Certified заменена автоматикой в 2015 году, охватив более 1500 проектов ([SWE гл. 11](https://abseil.io/resources/swe-book/html/ch11.html#history_of_testing_at_google)).

### D.6. Trunk-based development

Почти вся разработка идёт в head; релиз начинается с релизной ветки от последней «зелёной» сборки, исправления переносятся cherry-pick ([Henderson](https://arxiv.org/pdf/1702.01715), 2017). Долгоживущая dev-ветка есть менее чем у десяти команд из примерно тысячи ([SWE гл. 16, сноска 13](https://abseil.io/resources/swe-book/html/ch16.html#left_parenthesisnearlyright_parenthesis)). Релизные ветки используют многие команды: cherry-pick минимален, обратного слияния в trunk нет ([#what_about_release_branches](https://abseil.io/resources/swe-book/html/ch16.html#what_about_release_branchesquestion_mar)). Незавершённые функции коммитят в trunk и выключают в рантайме; видимость ограничивают средствами сборки; «build horizon» - каждое задание в продакшене пересобирается и переразвёртывается не реже раза в шесть месяцев (там же). Авторы прямо называют ставку на dev-ветки ради стабильности ошибочной и предлагают вместо неё тесты, CI и ревью ([#dev_branches](https://abseil.io/resources/swe-book/html/ch16.html#dev_branches)). Для организаций вне Google та же практика переложена на измеримые пороги в рекомендациях DORA: не более трёх активных веток, слияние в trunk минимум раз в день, без code freeze ([dora.dev](https://dora.dev/capabilities/trunk-based-development/); в профиле - [G-BR-003](../docs/git/branches.md)). Документацию ведут как код - правила, контроль версий, владельцы, ревью, баг-трекер; g3doc - Markdown-документы рядом с кодом с «датами свежести» и напоминаниями владельцу ([SWE гл. 10](https://abseil.io/resources/swe-book/html/ch10.html#documentation_is_like_code), [#deprecating_documents](https://abseil.io/resources/swe-book/html/ch10.html#deprecating_documents)); публичный след - docguide в styleguide с 2015-08-31.

### D.7. Крупномасштабные изменения (LSC) и автоматические исправления стиля

**LSC** - набор логически связанных изменений, который практически нельзя закоммитить атомарно; типы - чистка антипаттернов, замена устаревших API, обновление компилятора, миграция на новую систему; большинство не меняет поведение ([SWE гл. 22](https://abseil.io/resources/swe-book/html/ch22.html#what_is_a_large-scale_changequestion_ma)). Процесс: авторизация → создание изменений → шардирование → очистка ([The LSC Process](https://abseil.io/resources/swe-book/html/ch22.html#the_lsc_process)). Авторизация - короткий документ и рассылка комитету примерно из дюжины человек; комитет одобряет щедро и служит инстанцией для споров ([Authorization](https://abseil.io/resources/swe-book/html/ch22.html#authorization)). **Rosie** режет общее изменение по границам проектов и владельцев и ведёт каждый кусок через конвейер «тест → отправка → коммит» ([Sharding and Submitting](https://abseil.io/resources/swe-book/html/ch22.html#sharding_and_submitting)); «глобальные одобряющие» из корневого `OWNERS` проверяют шарды шаблонными инструментами, у локальных владельцев нет права вето на LSC ([Policies and Culture](https://abseil.io/resources/swe-book/html/ch22.html#policies_and_culture), [SWE гл. 9](https://abseil.io/resources/swe-book/html/ch09.html#refactorings_and_large-scale_changes)). Инструменты генерации - ClangMR, JavacFlume, Refaster; анализ кода - через Kythe; эмпирическое правило: больше 500 правок - выгоднее освоить инструмент, чем править вручную ([Codebase Insight](https://abseil.io/resources/swe-book/html/ch22.html#codebase_insight); [ClangMR](https://research.google/pubs/large-scale-automated-refactoring-using-clangmr/), 2013). Тестирование: «TAP train» каждые три часа - каждое изменение сначала проходит 1000 случайных тестов, затем прошедшие объединяются в общий прогон ([Testing LSCs](https://abseil.io/resources/swe-book/html/ch22.html#testing-id00096)). Масштаб: 10-20 % изменений в проекте - результат LSC (≈2019); Rosie позволяет проводить тысячи изменений в день, инфраструктуру поддерживают несколько десятков инженеров ([Conclusion](https://abseil.io/resources/swe-book/html/ch22.html#conclusion-id00026)). Связь со стилем прямая: машинные правки должны выглядеть как человеческие, отсюда необходимость гайдов и автоформаттеров ([Change Creation](https://abseil.io/resources/swe-book/html/ch22.html#change_creation)); неоднородность - разные VCS, CI и правила форматирования по проектам - названа препятствием для LSC ([Heterogeneity](https://abseil.io/resources/swe-book/html/ch22.html#heterogeneity)). Устаревание API бывает рекомендательным и принудительным; принудительное обеспечивает команда, которая сама мигрирует пользователей; откат к старому API предотвращают Tricorder и списки видимости в системе сборки ([SWE гл. 15](https://abseil.io/resources/swe-book/html/ch15.html#compulsory_deprecation), [#preventing_backsliding](https://abseil.io/resources/swe-book/html/ch15.html#preventing_backsliding)).

Интерпретация: автоисправление стиля у Google - не отдельный инструмент, а цепочка: форматтер в presubmit для нового кода, Tricorder с кнопкой исправления для замечаний в ревью, LSC для уже написанного кода, а перед включением новой проверки компилятора - автоматическая чистка всей кодовой базы. Это объясняет, почему публичные гайды могут ужесточаться без переходного периода: внутри кодовая база приводится к новому правилу машиной.

### D.8. Что переносится на обычный git-репозиторий, а что имеет смысл только в монорепозитории

Переносятся практики, которые опираются на дисциплину и стандартные возможности площадок; не переносятся практики, требующие единого дерева, единого графа зависимостей и выделенной инфраструктурной команды. ## E. Происхождение и конфликты

### E.1. На какие внешние гайды опираются правила Google и чем от них отличаются

**Языковые гайды.** Публичные гайды Google - экспорт внутренних документов, и на внешние своды они почти не ссылаются. C++-гайд - самостоятельный документ; самое известное решение - отказ от исключений - он объясняет практикой, а не принципом: существующий код Google не рассчитан на исключения, перевод слишком дорог, а открытым проектам исключения не рекомендуются, чтобы их можно было использовать внутри компании; при старте с нуля решение, вероятно, было бы другим ([Exceptions](https://google.github.io/styleguide/cppguide.html#Exceptions)). От C++ Core Guidelines гайд расходится принципиально в двух местах - исключения и стиль имён - и совпадает в положении `T* p`, `explicit`-конструкторах и возврате значений вместо выходных параметров (таблица - в B.5). Python-гайд - не надстройка над PEP 8: с PEP 8 он совпадает в основном (4 пробела, `CapWords` и `lower_with_under`, `is None`) и с сентября 2026 года прямо на него ссылается в разделе об именах, но отличается трёх видов: параметры (80 символов против 79 и 72 для докстрингов); запреты, которых в PEP 8 нет (импорт только модулей, отказ от относительных импортов, которые PEP 8 называет приемлемыми, `staticmethod`, несколько `for` в comprehension, f-строки в логах); и то, чего PEP 8 не касается (формат докстринга, обязательный линтер, проверка типов, формат `TODO`, точка входа `main()`). С Black гайд расходится только длиной строки (80 против 88). Внутренняя история Python-гайда показывает обратное движение - к сообществу: отступ 2 и `CamelCase` для методов, введённые ради согласованности с C++, уступили `snake_case` и, для Starlark, четырём пробелам из-за трудностей при открытии кода ([SWE гл. 8](https://abseil.io/resources/swe-book/html/ch08.html#setting_the_standard)).

C#-гайд прямо называет источники: именование - Microsoft C# naming guidelines и CoreFX coding guidelines, пробелы - Google Java Style, переносы - Google C++ Style ([csharp-style](https://google.github.io/styleguide/csharp-style.html)). Go Style предполагает знакомство с Effective Go и расширяет его; Go Code Review Comments, в свою очередь, ссылается на гайд Google как на более подробный. Swift-гайд включает Swift API Design Guidelines целиком и добавляет форматирование, которого там нет. R-гайд - форк Tidyverse Style Guide. Java-, Kotlin- и TypeScript-гайды самостоятельны и строже норм сообщества: 2 пробела и 100 колонок против 4 и 80 у Oracle; запрет wildcard-импортов и лимит 100 колонок, которых нет в Kotlin Coding Conventions; запрет `export default`, тогда как Airbnb предпочитает default-экспорт для модуля с одним экспортом.

**Фреймворки.** Гайд Angular связан с TS-гайдом Google двусторонне, но слабо: Angular не требует следовать TS-гайду, а советует с ним свериться; TS-гайд упоминает Angular в трёх местах - свойства, которые читает шаблон, не должны быть `private` ([tsguide](https://google.github.io/styleguide/tsguide.html#properties-used-outside-of-class-lexical-scope)), новые декораторы определять нельзя, разрешены только фреймворковые ([tsguide](https://google.github.io/styleguide/tsguide.html#decorators)), фреймворк-коду оставлено исключение для `prototype`. Где оба говорят об одном, они согласованы (`protected` для членов шаблона, `readonly`, именованные экспорты), и TS-гайд строже: у Angular «prefer `protected`», у Google - «must not use `private`», отсюда MUST у [G-NG-022](../docs/frameworks/angular.md). Документы репозитория Angular называют разную основу - coding standards ссылаются на JavaScript-гайд Google, CONTRIBUTING - на TypeScript-гайд ([coding-standards.md](https://github.com/angular/angular/blob/main/contributing-docs/coding-standards.md), [CONTRIBUTING.md](https://github.com/angular/angular/blob/main/CONTRIBUTING.md#rules)); оба относятся к разработке фреймворка, а не приложений. Для React конфликт возникает между TS-гайдом Google и привычками React: примеры react.dev построены на `export default` и файлах вида `Gallery.js`, для props допускаются и `type`, и `interface`; профиль везде берёт вариант Google.

**Репозиторий и git.** Текст заголовка лицензии - стандартный шаблон из приложения к Apache-2.0; собственного в нём только строка `Copyright <год> Google LLC` и схема `https`. Кодекс поведения шаблона new-project - Contributor Covenant 1.4 с добавленным разделом «Conflict Resolution» и пунктом о спаме, а «Community Guidelines» организации - адаптация IndieWeb Code of Conduct ([google/.github](https://github.com/google/.github/blob/master/CODE_OF_CONDUCT.md)). Соглашение о вкладе - собственный CLA Google: это лицензия, а не передача прав, и DCO в документах Google не упоминается. Шаблоны политики безопасности следуют практике координированного раскрытия с 90-дневным сроком. Docguide ссылается на CommonMark, переносит на Markdown привычки работы с кодом (80 колонок), а за регистром заголовков отсылает к developer documentation style guide; тот ставит выше себя правила проекта, а ниже - Merriam-Webster, Chicago Manual of Style и Microsoft Writing Style Guide. Проверки, которыми профиль закрывает правила репозитория (`License`, `Security-Policy`, `Branch-Protection`, `Pinned-Dependencies`), принадлежат OpenSSF Scorecard - проекту сообщества, начатому при участии Google. Цепочка Conventional Commits документирована самим стандартом: его страница «About» сообщает, что спецификация основана на правилах коммитов Angular ([About](https://www.conventionalcommits.org/en/about/)); пресет `@commitlint/config-conventional` тоже ссылается на конвенцию Angular; release-please читает историю в этом формате и пересчитывает типы в версию по [SemVer](https://semver.org/). Сам Angular проверяет сообщения собственным `ng-dev`, а не commitlint. Статья cbea.ms - внешняя: её рекомендуют README стайлгайдов, документ Chromium и гайд JAX. Правила ревью - экспорт внутреннего документа: README eng-practices объясняет внешнему читателю термины CL и LGTM. Trunk-based development - описание внутренней практики (SWE гл. 16), переложенное на измеримые пороги в DORA.

**ML.** Области ML, NB и REPRO не наследуют ни одному внешнему стайлгайду: это компиляция из принципов Google 2015-2017 годов, документации библиотек и практики репозиториев. Правила MLOps выстроены в цепочку: статья о техдолге (короткая версия - 2014 год) → Rules of ML → ML Test Score → TFX как реализация (блог TensorFlow называл TFX попыткой буквально закодировать Rules of ML, [2020-09-25](https://blog.tensorflow.org/2020/09/brief-history-of-tensorflow-extended-tfx.html)) → документ Google Cloud об уровнях зрелости → whitepaper 2021 года. Документы пересекаются: требование общего кода для обучения и обслуживания есть в Rules of ML (№ 32) и в TFX (компонент Transform); проверка модели перед выкладкой - в Rules of ML (№ 9), в рубрике ML Test Score (Infra 4) и в TFX (Evaluator). Внешних гайдов в основе нет; исключение - Keras API design guidelines, которые берут соглашения об именах у NumPy. Внешние источники - Cookiecutter Data Science, nbstripout и jupytext, документация PyTorch и scikit-learn, MLflow, DVC - использованы только для пробелов и помечены «не Google». Интерпретация: они закрывают те места, где у Google есть принцип, но нет инструмента вне его облака.

### E.2. Конфликты между источниками и выбор профиля

Общая закономерность (интерпретация): инструменты, которые правят сами инженеры Google или чьё поведение вписано в текст гайда, отстают от гайда на дни или месяцы (clang-format, pyink); те, что Google сопровождает «по мере возможности» (`pylintrc`) или не сопровождает (cpplint, yapf, pytype, gts), расходятся надолго. Поэтому профиль объявляет источником истины текст гайда, а конфиги - приближением с перечнем расхождений. ## F. MLE и MLOps

### F.1. Что есть и чего нет

**Единого «ML style guide» у Google нет.** Google Python Style Guide не содержит ни одного ML-специфичного правила: слова ML, JAX, Colab и notebook в нём не встречаются, TensorFlow фигурирует только в примерах ([§3.19.6](https://google.github.io/styleguide/pyguide.html#s3.19.6-type-aliases)). Публичные ML-практики Google - это слои разных лет. Нижний слой - принципы 2014-2017 годов: статья о скрытом техдолге ([NIPS 2015](https://proceedings.neurips.cc/paper_files/paper/2015/file/86df7dcfd896fcaf2674f757a2463eba-Paper.pdf); короткая версия - 2014), 43 правила Мартина Зинкевича ([Rules of ML](https://developers.google.com/machine-learning/guides/rules-of-ml), выросли из доклада на [NIPS 2016](https://neurips.cc/virtual/2016/8539)) и рубрика из 28 тестов ([ML Test Score](https://storage.googleapis.com/pub-tools-public-publication-data/pdf/aad9f93b86b7addfea4c419b9100c6cdd26cacea.pdf), 2017). Из них жив только гайд: страница обновлена 2025-08-25 и распространяется под CC BY 4.0; статьи не имеют открытой лицензии и годятся только для пересказа. Средний слой - архитектурная документация Google Cloud 2021-2025 годов: [уровни зрелости 0/1/2](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) (ревизия 2024-08-28), [лучшие практики](https://docs.cloud.google.com/architecture/ml-on-gcp-best-practices) (2024-09-09), раздел Well-Architected Framework (2025-04-28) и whitepaper 2021 года; к нему же относятся модули «Production ML systems» в ML Crash Course. Верхний слой - гайды и конфиги отдельных проектов (TensorFlow, Keras, JAX, Flax, TFX, TFDV, Kubeflow Pipelines) и фактическая практика репозиториев.

Почти все эти тексты формулируют рекомендации, а не требования. Поэтому из 31 правила области MLOPS уровень MUST имеют три: запрет секретов в репозитории ([G-MLOPS-004](../docs/ml/mlops.md), по гайду Google Open Source о чистке перед публикацией) и два правила для C++-операций TensorFlow, где источник пишет «must» (G-MLOPS-029, G-MLOPS-030); из 17 правил ML и 19 правил REPRO MUST нет ни одного, из 13 правил NB - два. Рубрика ML Test Score вошла в профиль целиком как критерий готовности к продакшену (G-MLOPS-019): 0,5 балла за тест, выполненный вручную, 1 балл за автоматический, итог - минимум по четырём группам.

**Статусы, которые важно знать.** TFX не в архиве, но развивается медленно: в 2026 году вышли 1.17.3 и 1.21.0 ([RELEASE.md](https://github.com/tensorflow/tfx/blob/master/RELEASE.md)), файл [`ROADMAP.md`](https://github.com/tensorflow/tfx/blob/master/ROADMAP.md) не менялся с 2022-03-24 (последняя запись - Q2 2022; проверено по истории git 2026-10-16), официального заявления о статусе нет; в рекомендациях Google Cloud по оркестрации он уже не назван - там управляемые Pipelines и Kubeflow Pipelines SDK. Vertex AI в апреле 2026 года переименован в Gemini Enterprise Agent Platform; первичный анонс не открывался, переименование видно по заголовкам документации и по [вторичному источнику](https://www.hpcwire.com/aiwire/2026/04/23/google-unveils-gemini-enterprise-agent-platform/). Model Card Toolkit в архиве с 2024-09-27, Data Cards Playbook не обновляется с 2023-02-22, gin-config не имеет релизов на PyPI с 2021-11-03, Keras API design guidelines не менялись по существу с 2020 года. Интерпретация: принципы стабильны, а инструментальная привязка меняется быстрее, чем обновляются тексты, поэтому профиль опирается на принципы, а инструменты называет как примеры (G-MLOPS-008 … G-MLOPS-011).

**Чего нет.** Публичных данных не найдено по следующим темам: нормативная раскладка каталогов ML-проекта; официальная рекомендация, какую библиотеку конфигурации выбирать, и заявление об устаревании gin; соглашение о записи форм тензоров в аннотациях, комментариях или именах; общий «Colab style guide», правила именования ноутбуков и явное правило о переносе кода из ноутбука в модули; общий гайд о фиксации окружения ML-проекта; правило «не коммитьте данные и веса в git» (есть рекомендации, где хранить каждый вид артефактов, и практика примеров Flax, но не запрет - а контрпример `google-research` держит датасеты в git); Git LFS и DVC (Google о них не пишет, правило G-MLOPS-003 целиком «не Google»); процедура отката модели (упомянута в четырёх источниках одной-двумя фразами, отдельного документа нет); стайлгайд для C++-кода LiteRT и XLA; актуальный Markdown-шаблон model card; детерминизм JAX на GPU. Тела продуктовых страниц Model Monitoring, Model Registry и Experiments получить не удалось, поэтому пороги по умолчанию и детали выкладки в профиле не приводятся.

### F.2. Стиль ML-кода: структура, граница исследования и продакшена

Нормативного шаблона раскладки каталогов - публичных данных не найдено. Ближайший образец - примеры Flax: README каталога прямо говорит, что все примеры устроены одинаково, чтобы знание одного переносилось на остальные ([examples/README.md](https://github.com/google/flax/blob/main/examples/README.md)). По клону на коммите `6c9494b` (2026-10-07) из 14 каталогов `examples/` 11 следуют шаблону «`configs/` + исполняемый модуль с `config_flags` + библиотечный модуль обучения» (`main.py` + `train.py` - 10, плюс `ppo` с `ppo_main.py`); README - у 12, `requirements.txt` - у 12, тесты `*_test.py` - у 10, `input_pipeline.py` - у 9, `models.py` - у 9, рядом лежит ноутбук - у 5, флаг `workdir` - у 10 из 11. Точка входа намеренно короткая: логика живёт в библиотеках, которые можно тестировать и импортировать в Colab ([main.py](https://github.com/google/flax/blob/main/examples/mnist/main.py)); отсюда [G-ML-001 … G-ML-003](../docs/ml/project-structure.md).

**Исследовательский код оформлен заметно мягче.** Монорепозиторий google-research на коммите `72ffe35` (2026-10-08) содержит 755 каталогов-проектов (23 236 путей); его CONTRIBUTING требует только CLA и ревью, стилевых требований нет ([CONTRIBUTING.md](https://github.com/google-research/google-research/blob/master/CONTRIBUTING.md)). README есть у 735 проектов (97 %), `requirements.txt` - у 468 (62 %), `run.sh` - у 288 (38 %), тесты - у 220 (29 %), ноутбуки - у 186 (25 %), `setup.py` или `pyproject.toml` - у 47 (6 %), файлы `.gin` - у 42 (6 %). Интерпретация: граница «исследовательский код → продакшен» у Google проходит между репозиториями, а не внутри одного; профиль переносит её внутрь репозитория правилом G-ML-004. Письменные опоры для границы - правило № 4 из Rules of ML (сначала простая модель и инфраструктура; G-ML-005) и категории долга из «Hidden Technical Debt»: мёртвые экспериментальные ветки (G-ML-006) и обвязочный код вокруг чужих пакетов (G-ML-007). Пробелы раскладки закрывает Cookiecutter Data Science v2 - «не Google».

### F.3. Конфиги экспериментов

У Google три open-source-библиотеки конфигурации и ни одной рекомендации, какую выбирать. gin-config (DSL `.gin` и dependency injection) жив как репозиторий, но последний релиз на PyPI - 0.5.0 от 2021-11-03 с классификаторами Python 2.7 и 3.5-3.7 ([PyPI](https://pypi.org/project/gin-config/)). ml_collections (`ConfigDict`, `config_flags`) активен: v1.1.0 от 2025-04-17. Fiddle (конфиг как граф вызовов Python) активен: HEAD 2026-10-05. Общий знаменатель - absl: флаги и точка входа `app.run(main)`. Практика: все 11 примеров Flax с конфигом используют ml_collections (`config_flags.DEFINE_config_file`, по умолчанию `lock_config=True`); Dopamine, Trax и T5X - gin; T5X - ещё и Fiddle. В google-research по 468 файлам `requirements.txt` из корней проектов `absl-py` указан в 270, `ml-collections` - в 49, `gin-config` - в 44, `clu` - в 32, `fiddle` - в 3, Hydra и OmegaConf - ни в одном (нижняя оценка). Профиль берёт absl + ml_collections (G-ML-009, G-ML-010), оставляет gin для существующего кода (G-ML-013), заимствует у Fiddle принцип «библиотечный код принимает обычные аргументы и о конфигурации не знает» (G-ML-011, [flags_code_lab.md](https://github.com/google/fiddle/blob/main/docs/flags_code_lab.md#how-to-structure-your-code)) и требует хранить конфиги в репозитории под ревью (G-ML-008) - единственный явно нормативный пассаж «Hidden Technical Debt» §6. Правило «флаги только в исполняемом модуле» (G-ML-012) - реконструкция из практики Flax (9 из 11; `nlp_seq` и `seq2seq` объявляют флаги ещё и в `train.py`); гайд absl описывает противоположную модель.

### F.4. Типизация тензоров и docstrings

Официального соглашения о записи форм тензоров - публичных данных не найдено. `jax.typing` даёт только типы «массив или не массив» ([jax.typing](https://docs.jax.dev/en/latest/jax.typing.html#jax-typing-best-practices)), а Chex прямо исходит из того, что аннотации не выражают ранг, форму и dtype, и предлагает runtime-проверки ([chex README](https://github.com/google-deepmind/chex/blob/master/README.md)); отсюда G-ML-014 и [G-LIB-022](../docs/ml/libraries.md). Формы и dtype у Google документируют словами: гайд TensorFlow требует описывать в `Args` и `Returns` тип, смысл, возможные формы, dtype и ранги ([code style](https://www.tensorflow.org/community/contribute/code_style)); отсюда G-ML-016. Требование примера кода в docstring - из Keras API design guidelines (G-ML-017). Проверка типов расходится с Python-гайдом: гайд называет pytype (в архиве с 2026-09-03), JAX перешёл на Pyrefly, в Orbax остался хук pytype. Альтернатива «не Google» для форм в аннотациях - jaxtyping (статус не проверялся).

### F.5. Ноутбуки

Единственный свод правил, который и записан, и проверяется CI, лежит в `tensorflow/docs`: шаблон ноутбука, форматтер `nbfmt`, линтер `nblint` и джоб `outputs-removed`, который не пропускает изменённые ноутбуки с output-ячейками (исключение - один файл) ([ci.yaml](https://github.com/tensorflow/docs/blob/master/.github/workflows/ci.yaml)). Остальные репозитории поступают иначе. JAX и Flax держат документационные ноутбуки парой `.ipynb` + `.md` через jupytext ([JAX developer docs](https://docs.jax.dev/en/latest/developer.html#update-notebooks)); Flax запускает nbstripout с `--keep-output`, то есть чистит только метаданные. Подсчёт по клонам на 2026-10-09: во Flax выводы сохранены в 35 из 45 ноутбуков, в паре с `.md` - 36, ссылка на Colab - в 13; в JAX - 19 из 41, 32 и 16 соответственно; в google-research ноутбуки есть у 186 из 755 проектов, выводы сохранены в 162 из 335 ноутбуков (48 %; хотя бы один такой ноутбук - у 101 проекта из 186), пар jupytext нет, блок `metadata.colab` - у 282 из 335, а ни pre-commit-конфига, ни `.gitattributes` в репозитории нет. Профиль запрещает выводы в рабочих ноутбуках ([G-NB-001](../docs/ml/notebooks.md), MUST - потому что проект-источник проверяет это в CI), допускает их в документационных при парном хранении (G-NB-009, G-NB-010), а критерий переноса кода формулирует сам с опорой на пример Flax, «prototype smell» и Cookiecutter Data Science (G-NB-011, G-NB-012). nbstripout и jupytext - не инструменты Google, но ими пользуются его репозитории.

### F.6. Воспроизводимость и окружение

Требование воспроизводимости есть в «The ML Test Score» (тест Infra 1) и раскрыто в ML Crash Course: сидировать генераторы, инициализировать компоненты в фиксированном порядке, усреднять несколько запусков, держать код в системе контроля версий ([deployment testing](https://developers.google.com/machine-learning/crash-course/production-ml-systems/deployment-testing)); отсюда [G-REPRO-001 … 003, 009, 011, 016](../docs/ml/reproducibility.md). Рецепты фреймворков - `keras.utils.set_random_seed` и `tf.config.experimental.enable_op_determinism` (G-REPRO-004, 005), явные ключи JAX с деревом «широким, а не глубоким» (G-LIB-018, G-REPRO-006). Побитовой воспроизводимости не обещает никто: TensorFlow оговаривает то же железо и ту же версию ([config.py](https://github.com/tensorflow/tensorflow/blob/master/tensorflow/python/framework/config.py)), Keras 3 - разные случайные числа у бэкендов при одном сиде. О детерминизме JAX на GPU публичных данных не найдено. Сиды PyTorch и `random_state` scikit-learn - G-REPRO-007 и 008, «не Google».

**Окружение.** Общего гайда Google о фиксации окружения ML-проекта публичных данных не найдено. Есть README TensorFlow о собственной сборке: все транзитивные зависимости закреплены вместе с хешами ради воспроизводимой сборки ([Managing hermetic Python](https://github.com/tensorflow/tensorflow/blob/master/ci/official/requirements_updater/README.md)) - тот же принцип герметичности, что у Bazel (D.5). Из восьми просмотренных ML-репозиториев (tensorflow, keras, jax, flax, optax, chex, orbax, tfx) lock-файлы с хешами держат два - tensorflow и jax; у flax есть только `flaxlib_src/uv.lock`. В google-research из 468 файлов `requirements.txt` точные версии у всех зависимостей указаны в 64 (14 %), частично - в 102, только диапазоны - в 212, без версий - 85, хешей нет ни в одном; в примерах Flax полностью закреплённых `requirements.txt` - 8 из 12. Правила G-REPRO-012 и G-REPRO-013 поэтому помечены как реконструкция, G-REPRO-013 - с низкой уверенностью.

**Трекинг экспериментов.** Письменный источник один - Deep Learning Tuning Playbook, гайд исследователей с оговоркой «not an officially supported Google product»: поля записи об эксперименте и выбор лучшего чекпойнта задним числом ([tuning_playbook](https://github.com/google-research/tuning_playbook#setting-up-experiment-tracking)); отсюда G-REPRO-017 и G-REPRO-019. Документация Google Cloud рекомендует TensorBoard и продукт Experiments ([best practices](https://docs.cloud.google.com/architecture/ml-on-gcp-best-practices#use-tensorboard-and-experiments-to-analyze-experiments)); тело страницы самого продукта получить не удалось. В коде Google инструмент по умолчанию - TensorBoard: 10 из 11 примеров Flax пишут метрики в его журнал (4 через `flax.metrics.tensorboard`, 6 через `clu.metric_writers`), 7 из 11 сохраняют туда же гиперпараметры, сид задан в конфиге у 5 из 11; в `requirements.txt` google-research `tensorboard` встречается в 49 файлах, `wandb` - в 5, `mlflow` - ни в одном. MLflow в профиле - альтернатива «не Google».

### F.7. ML-библиотеки

Антипаттерны у библиотек Google записаны в документации явно. У TensorFlow это гайд по `tf.function` (побочные эффекты Python, повторная трассировка, накопление в списках - G-LIB-001 … 003), у JAX - «The Sharp Bits» (чистота функций, неизменяемые массивы, статические формы - G-LIB-016, 017, 020) и новые страницы о ключах случайных чисел и потоке управления (G-LIB-018, 019), у Keras - гайды по сериализации (G-LIB-010 … 012) и Keras API design guidelines (G-LIB-014, 015), у Flax - гайды NNX (G-LIB-025 … 027). Свежесть источников разная: гайды TensorFlow не обновлялись с 2024 года при живых релизах (v2.21.0 от 2026-03-04); гайды keras.io датированы 2023 годом; документация JAX перестроена по уровням (101, 201 и далее; у новых страниц метка проверки 2026-07-09), а прежние страницы о случайных числах, потоке управления и отладке сохранены по старым адресам и названы в репозитории неподдерживаемыми (`docs/superseded.rst`, проверено 2026-10-09). Keras API design guidelines - документ 2020 года без лицензии; он описывает проектирование API самой Keras, а профиль применяет его к собственным слоям. Keras 3 (v3.15.1) работает на JAX, TensorFlow, PyTorch и OpenVINO, а `tf.keras` с TensorFlow 2.16 по умолчанию означает Keras 3 ([keras.io](https://keras.io/keras_3/)); отсюда правило не смешивать его с `tf_keras` (G-LIB-013). Flax рекомендует новым пользователям NNX, не объявляя Linen устаревшим (G-LIB-025); `flax.training.checkpoints` объявлен устаревшим в 2023 году в пользу Orbax. Для PyTorch, scikit-learn и Hugging Face правил Google нет; семь правил G-LIB-028 … 034 взяты из гайдов самих проектов и помечены «не Google».

Всего в области LIB 34 правила, уровень MUST у восьми (правила JAX - по словам источника «requires» и «never»; G-LIB-013 - по формулировке «невозможно»; G-LIB-031 для scikit-learn - по слову «never»). Автоматически проверяется малая часть: `assert` в проверке ввода (ruff `S101`), вызовы `pickle` (ruff `S301`), число аргументов (ruff `PLR0913`), запрещённые импорты (ruff `TID251`). Остальное ловят тесты и ревью, а часть нарушений - сама библиотека ошибкой времени выполнения.

### F.8. MLOps: пайплайны, CI/CD, реестр, документация, C++

**Пайплайны и CI/CD.** Документ Google Cloud об уровнях зрелости описывает шкалу автоматизации, а не чек-лист: уровень 0 «Manual process» - все шаги на скриптах и ноутбуках, модель передаётся инженерам вручную, релизы несколько раз в год, нет CI, CD и мониторинга предсказаний; уровень 1 «ML pipeline automation» - оркестрованный пайплайн из модульных, в идеале контейнеризованных компонентов, непрерывное обучение по триггерам, один и тот же пайплайн в разработке и продакшене, валидация данных и модели, хранилище метаданных с указателем на предыдущую модель; уровень 2 «CI/CD pipeline automation» - тесты и сборка самого пайплайна, реестр моделей, автоматический деплой в test, полуавтоматический в pre-production, ручной в production ([MLOps doc](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning), 2024-08-28). Документ не говорит, что уровень 2 обязателен для всех. Для репозитория без облака Google переносимы CI-тесты уровня 2 - юнит-тесты логики признаков, сходимость на нескольких примерах, отсутствие NaN, ожидаемые артефакты каждого компонента - и CD-проверки: совместимость с инфраструктурой, тест API предсказаний, нагрузка, порог качества до выкладки. Документ о TFX, Pipelines и Cloud Build показывает тот же процесс на конкретных инструментах. Профиль формулирует принципы без привязки к платформе (G-MLOPS-008 … 011): пайплайн как код под ревью, общий код преобразований для обучения и обслуживания (Rules of ML № 32, компонент Transform), проверка модели перед выкладкой (Rules of ML № 9, Infra 4, Evaluator), контейнеры с тегом по SHA. Тесты данных и моделей - рубрика ML Test Score целиком (G-MLOPS-019) и тесты инфраструктуры (G-MLOPS-013). Мониторинг и дрейф описаны в ML Crash Course, whitepaper 2021 года (schema skew, distribution skew, data drift, concept drift) и документации Model Monitoring (G-MLOPS-020); откат описан косвенно - указатель на предыдущую модель в метаданных и фраза о «review, approve, release, and roll back» в whitepaper - отдельной процедуры нет.

**Документация моделей и данных.** У model card три набора заголовков: девять разделов [статьи 2019 года](https://arxiv.org/abs/1810.03993), схема архивного Model Card Toolkit и структура действующих карточек [Gemma](https://ai.google.dev/gemma/docs/core/model_card_3) и Gemini, где вместо разделов о факторах и количественном анализе стоят блоки об оценке безопасности. [Шаблон профиля](../templates/ml/MODEL_CARD.md) собран из первого и третьего набора и дополнен блоком об эксплуатации (G-MLOPS-025). [Data card](../templates/ml/DATA_CARD.md) опирается на Playbook (G-MLOPS-026) с пометкой о его возрасте; из Playbook взяты только названия тем, и, если считать шаблон производным произведением от материала под CC BY-SA 4.0, на него распространяется условие share-alike - вопрос отмечен для NOTICE профиля.

**Что нельзя коммитить.** Запрет секретов - MUST по императиву гайда Google Open Source о чистке перед публикацией (G-MLOPS-004); проверка - gitleaks и `check-added-large-files` из pre-commit-hooks, оба «не Google». Данные и веса - в объектном хранилище по рекомендации Google Cloud (G-MLOPS-002), выводы ноутбуков - по G-NB-001; Git LFS и DVC - целиком «не Google» (G-MLOPS-003).

**C++ в ML.** Отдельного гайда нет: TensorFlow отсылает к Google C++ Style Guide и `clang-format` со стилем Google (G-MLOPS-027) и добавляет короткий документ о возврате ошибок через `tensorflow::Status` (G-MLOPS-028); этот документ состоит из одного коммита от 2020-05-04 (проверено по истории `tensorflow/community`), и соблюдает ли текущий код TensorFlow запрет `StatusOr<T>`, не проверено. Правила для custom ops взяты из гайда «Create an op» (G-MLOPS-029 … 031); репозиторий-шаблон `tensorflow/custom-op` не обновлялся с 2021-03-18. Стайлгайда для C++-кода LiteRT и XLA - публичных данных не найдено.
